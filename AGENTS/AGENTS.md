# AGENTS.md — 神姫PROJECT チャート作成ツール

最終更新：2026-11-11

このファイルは、本リポジトリで作業するエージェント（Claude など）と開発者向けの仕様書兼作業ガイドです。実装の進め方は §16 を参照。キャラごとの資料と定義は `CHARACTER.md`、説明文から定義 JSON を作る手順は `CHARACTER_DATA_GUIDE.md`、効果 DSL の部品の一覧表は `DSL_PARTS.md`（いずれも本ファイルと同じ `AGENTS/` ディレクトリ）、開発環境の構築手順はリポジトリ直下の `SETUP.md` に分けている。
**仕様は「確定」「仮置き」「未確定」を区別して記載しています。未確定の項目を勝手に決めて実装しないこと。** 必要な場合は仮置きであることをコード上に明記（`// TODO(spec): ...`）し、本ファイルの「未確定事項」を参照すること。

## 1. 目的とスコープ

### 目的
『神姫PROJECT』のバトルで、**各ターンに誰の何（アビリティ／バースト／通常攻撃／幻獣）を使うか**をチャートとして組み立て、その計画が実行可能かを検証・共有するツール。

### スコープ内
- 編成登録（神姫・英霊・幻獣）
- **ゲーム画面に似たプレイ画面**（§14.0）での操作。プレイヤーはチャートを直接入力せず、ゲームと同じ感覚でアビ・攻撃を操作する。その操作の記録がチャートになる
- 記録したチャートの閲覧（ターン表・ガントチャート）と、途中のターンへの巻き戻し・やり直し
- 行動の分岐（git のブランチのように別案を枝分かれさせて保持する。§4.12）
- 各時点の状態の追跡（CT、バーストゲージ、バフ／デバフ、トークン、使用回数）
- 行動の使用可否判定（使えない行動を警告表示）
- 連撃などの確率要素を含む**チャート成功確率**の算出（モンテカルロ法）と、失敗箇所の集計
- チャートの保存・共有（localStorage、JSON 入出力、URL 共有）

### スコープ外（初期版）
- キャラデータの外部投稿受付（§12。当面はリポジトリ内の JSON を開発者が直接編集する）
- ダメージ量の計算（DMG 系効果は「発生した」ことのみ記録）
- 敵 AI・敵行動の再現（必要な影響は**手入力イベント**として扱う）
- HP の厳密な増減（HP を条件にする効果のために、HP 割合の手入力だけは扱う。§4.11）

## 3. アーキテクチャの原則

1. **計算エンジンは UI から完全に分離する。** `src/engine/` はフレームワーク非依存の純粋な TypeScript とし、DOM や UI ライブラリを import しない。
2. **エンジンは決定的にする。** 乱数は外部から注入する（`rng: () => number`）。
   - 通常表示：最低保証（連撃は 1 段）で計算する。
   - 成功確率：同じエンジンを乱数ありで多数回実行する。
3. **使用可否フラグは状態として持たない。** CT・使用回数・トークン・ゲージなどから**毎回計算**する（二重管理を避ける）。
4. **データにコードを書かせない。** キャラ定義 JSON は効果を名前で参照するだけ。実処理はエンジン側の登録表（registry）に置く。投稿データに JS を含めたり `eval` したりしてはならない。
5. **イベント駆動。** アビリティ使用・攻撃・被弾・ターン開始/終了などはイベントとして発行し、アシストのトリガーと回数制バフの消費はこのイベントを購読して処理する。
6. **攻撃処理は 1 つのルーチンに集約する。** 通常攻撃・バーストは、攻撃フェーズからもアビリティ効果（`performAttack`）からも呼ばれる。どちらも同じ `performAttack(char, kind, options)` を通し、イベント発行・ゲージ上昇・連撃判定・回数制バフの消費を一元化する。攻撃フェーズ専用の処理を別に書かないこと。
7. **チャートデータを唯一の正とする。** チャートデータ（編成・操作の記録・手入力イベント・ユーザー補正）が唯一の正で、状態・警告・ガントチャートはすべてエンジンでチャートデータから再計算する派生データとする。プレイ画面（§14.0）での操作は、チャートデータに操作を 1 件追記し、エンジンで再計算して画面に反映する、という流れにする。プレイ画面が独自に状態を持ってはならない。Undo/Redo（§14.3）・巻き戻し・成功確率（操作の記録を乱数ありで再生する）はこの原則に依存する。
8. **連鎖の安全装置。** アシストの連鎖の挙動は実機未確認（§6.1-3 は「前に戻って発動する」、§6.1-4 は「アシストが生んだイベントでも後回しで発動する」で仮置き）。どの解釈でも止まるよう、1 アクションあたりの処理ステップに上限（例：1000）を設け、超えたらエラーとして報告する。

## 4. ドメインモデル

### 4.1 列挙値（確定）
- **属性**：火 / 水 / 風 / 雷 / 光 / 闇 / 幻
  - データ上の値：`fire` / `water` / `wind` / `thunder` / `light` / `dark` / `phantom`
  - **属性を持つのはキャラとダメージだけ**（確定）。アビリティそのものは属性を持たない。「雷属性の赤アビ」のような数え方は、「雷属性のキャラが使った赤アビ」と解釈する。ダメージの属性は、指定がなければ使ったキャラの属性になる（§10.2）。
- **色（アビリティ）**：赤 / 黄 / 青 / 緑 / 紫
- **攻撃区分**：通常攻撃 / アビリティ / バースト
  - 攻撃区分は**アビリティではなく、個々のダメージに付く**属性である。同じ「ダメージ」でも区分ごとに別物として数えられ、区分別の回数を条件にするアシストが存在する。
  - ダメージ効果（`damage`）は必ず区分を持つ。省略時は発生源から継承する（アビリティ → アビリティ、バースト → バースト、通常攻撃 → 通常攻撃、アシスト → 未確定 §11）。

### 4.2 キャラクター（神姫・英霊）の定義
- 名前、種別 `kind`（`kamihime`：神姫／`hero`：英霊）、属性
- バースト（効果。`burst.effects` に効果の部品で書く。§10）
- バーストゲージ上限 `gaugeMax`：`100`（既定）または `200`
- バースト時のゲージ消費方式 `burstConsume`：`subtract100`（既定。100 だけ消費し余剰は残る）または `consumeAll`（全消費）
  - **説明文に断りがなければ、上限 100・100 消費**（確定。クライアント確認）。
- 固有トークン（0 種類以上）：名前、開始時の数、上限（任意）、表示するか（`hidden`。「即リキャ残り回数」のような内部カウンターとして使う場合は非表示にできる）、グループ（任意）
  - **トークンのグループ**：「紅・黄・蒼・翠の 4 種類があり、合計で 3 つまで」のように、複数の種類で上限を共有するトークンは `tokenGroups` にグループとして定義する（例：ベートーヴェンの旋律。`CHARACTER.md`）。
    ```json
    "tokenGroups": [{ "name": "旋律", "max": 3 }],
    "tokens": [
      { "name": "紅の旋律", "group": "旋律" }, { "name": "黄の旋律", "group": "旋律" },
      { "name": "蒼の旋律", "group": "旋律" }, { "name": "翠の旋律", "group": "旋律" }
    ]
    ```
  - 上限（種類ごとの `max`、グループの `max`）を超えて付与しようとした分は**破棄**する（新しく付与しようとした分が入らない。確定）。
- **キャラのオプション**（`options`）：専用武器の有無など、ユーザーの装備で効果が変わる項目を、キャラ定義に選択肢として書く。ユーザーはチャートごとに選ぶ（§4.9）。効果の中では条件 `option` で参照する（§10.1）。
  ```json
  "options": [{ "id": "exclusiveWeapon", "name": "専用武器", "type": "boolean", "default": false }]
  ```
  ```json
  { "type": "if", "cond": { "option": { "id": "exclusiveWeapon", "is": true } },
    "then": [{ "type": "gaugeUp", "target": "allAllies", "amount": 15 }],
    "else": [{ "type": "gaugeUp", "target": "allAllies", "amount": 10 }] }
  ```
- バーストの効果を**ユーザーが設定する**キャラは、`burst.userDefined: true` とする。武器でバーストが変わるのは**英霊だけ**（確定）なので、`userDefined` は英霊にだけ使う。`burst.effects` には既定の効果（ゲーム画面で確認した 1 つの武器のもの）を書き、ユーザーはチャートごとのユーザー補正で上書きできる（§4.9）。**初期版は既定の効果で固定**し、上書きの入力は後の版で作る（§15.3）。
- アビリティ（複数）
  - 色、CT、攻撃区分、使用条件、コスト、使用回数制限（1 ターン上限／戦闘上限、任意）、効果
  - コストは条件付きで書ける（§6「コスト」）
  - EX 枠のアビ（ゲーム画面で「EX」と表示され「EX設定」できるもの）は `ex: true` を付ける。EX 枠のアビは付け替えられる（確定）が、**初期版はキャラ定義に書いたアビで固定**する。付け替え（編成ごとにどの EX アビを付けるかを選ぶ設定）は後の版で作る（§15.3）。
- アシスト（複数）
  - トリガー、条件、コスト、回数制限、効果
  - **1 つのアシストを複数の項目に分けて書いてよい**。ゲーム上は 1 つのアシストでも、「リミッター解除時は〇〇／味方が赤アビ使用時は△△（1 ターン 15 回まで）」のように発動のきっかけや回数上限が違う部分があるときは、部分ごとに別の項目にする。`origin: { "kind": "assist", "index": 1 }` で元のアシストを示し、UI では 1 つのアシストとして表示する。回数上限は項目ごとに数える。
  - **アビの説明文にある常時効果**（「※〇〇を発動する度、再使用間隔 2 ターン短縮」など、そのアビを使わなくても働く効果）も、アシストの項目として書く。`origin: { "kind": "ability", "id": "<アビ ID>" }` で元のアビを示し、UI ではそのアビの説明として表示する。
  - 有効範囲 `activeIn`：`main`（既定）/ `sub` / `both`（§4.4 サブ時有効のアシスト）

### 4.3 幻獣の定義
- 召喚攻撃は **1 ターンに 1 体まで**。
- **英霊が戦闘不能だと召喚できない**。
- その他の項目（CT、効果、使用回数など）は未確定（§11）。

### 4.4 編成ルール（確定）
| 枠 | 人数 | 備考 |
|---|---|---|
| 英霊 | 1 | |
| メイン神姫・前衛 | 2 | |
| メイン神姫・後衛 | 2 | |
| サブ神姫 | 2 | メインが戦闘不能になったら、サブ 1 → サブ 2 の順に入れ替わる |

- 同名キャラは編成に入れられない（サブも含む）。
- 幻獣の枠数は未確定（§11）。

#### 戦闘不能と入れ替え（確定）
入れ替えには 3 つの経路がある。

| 経路 | 発生 | 入れ替えのタイミング |
|---|---|---|
| ① 戦闘不能による自動補充 | 敵の攻撃・スリップダメージ（毒・熱狂など）で HP 0 | ターンエンド処理（§5）。**新しいキャラが動けるのは次のターンから** |
| ② 交代アビリティ | 「サブと交代」効果を持つアビリティ | **即時**（アビリティ使用の瞬間）。**入ったキャラは同じターンにアビリティ・通常攻撃・バーストのすべてが可能** |
| ③ 意図的な退場 | かばう・自傷・防御ダウンなどで計画的に落とす | ①と同じ（結果として HP 0 になるため） |

#### 交代アビリティ（②）の詳細（確定）
- 「交代したキャラ」と「**生存しているサブの先頭**（基本はサブ 1）」の位置を**そのまま入れ替える**（スワップ）。
- 下がったキャラは、交代相手がもともといた枠（基本はサブ 1）に入る。他のサブはそのまま。
  - 例：サブ 1 に B、サブ 2 に C、前衛 1 の A が交代アビを使用 → 前衛 1 に B、サブ 1 に A、サブ 2 に C。
- 下がったキャラは戦闘不能とは違い、再登場しうる。

#### 補充・交代の優先順（確定）
- 戦闘不能による補充でも交代アビでも、**生存しているサブのうち先頭のキャラ**が優先して出る。
- そのため、交代で下がってサブ 1 に入ったキャラは、次に誰かが倒れる（または交代する）と最初に再登場する。
  - 上の例の後に前衛 2 が倒れたら、サブ 1 の A が前衛 2 に補充される。

#### サブで待機中・再登場時の状態
| 項目 | 挙動 | 状態 |
|---|---|---|
| CT | 待機中は**進まない**（下がる直前の残り CT を保持） | 確定 |
| HP・バーストゲージ | 保持し、再登場時に引き継ぐ | 確定 |
| バフ・デバフ | ⚠️ **情報が矛盾**（下記） | 未確定 |
| 再登場のきっかけ | 別のキャラの戦闘不能による補充、または交代アビリティ | 確定 |

> ⚠️ **バフ・デバフの扱いは提供情報が矛盾している。**
> - 情報 A：状態を維持したまま待機する。
> - 情報 B：控えに回った時点で原則解除される（消去不可の固有効果などは除く）。
>
> 実装は**情報 B（原則解除、消去不可は保持）を仮置き**とし、`// TODO(spec)` を付ける。実機で確認すること（§11）。

#### 初めて登場するサブの初期状態（確定）
- 戦闘開始時と同じ状態で登場する。全アビリティ **CT 0** で、登場したターンから使用可能（自動補充の場合は次のターンから行動）。
- ゲージは戦闘開始時と同じ **0**（§8.0）。
- 一度メインに出て下がったキャラが再登場する場合は、下がる直前の CT・HP・ゲージを引き継ぐ（上表）。

#### サブ時有効のアシスト（確定）
- アシストには「サブメンバー時にも有効」なものがある。
- アシストの定義に有効範囲 `activeIn`（`main` / `sub` / `both`）を持たせる。既定は `main`。
- サブ時専用の効果は、そのキャラがメインに出ると発揮されなくなる。

#### 補充のルール（確定）
- HP はスコープ外なので、①③は**手入力イベント**（「T1 の敵フェーズで前衛 1 が戦闘不能」など）としてチャートに書く。③は高難度やタイムアタックでよく使う戦術なので、チャート上で計画として扱えることが重要。
- 補充されるのは**戦闘不能になった枠**で、**サブ 1 → サブ 2** の順。誰と誰が入れ替わるかは指定できない。
- 同じターンに複数のメインが倒れた場合、**枠の並び順（左から）**で補充する。倒れた順番には依存しない。
  - 隊列は左から「英霊」「メイン 1（前衛 1）」「メイン 2（前衛 2）」「メイン 3（後衛 1）」「メイン 4（後衛 2）」。
  - 例：メイン 2 とメイン 4 が同じターンに倒れたら、メイン 2 の枠にサブ 1、メイン 4 の枠にサブ 2 が入る（メイン 4 が先に倒れていても同じ）。
- 補充されたキャラは、**その枠の行動順・バースト順を引き継ぐ**。
- プレイ画面の敵フェーズの入力パネル（§14.0）では、意図的に落とす戦術の計画用に「この組み合わせで落とすと、どの枠に誰が入り、行動順がどうなるか」を表示する。
- 戦闘不能による補充（①③）はターンエンド処理で行われるため、補充されたキャラが行動するのは次のターンから。
- サブが尽きた後にメインが倒れた場合、その枠は空になる。
- 英霊は入れ替わらない（サブが入るのはメイン神姫の枠のみ）。
- 英霊が戦闘不能だと幻獣を召喚できない（§4.3）。英霊が倒れた後は、そのまま英霊の枠が空いた状態で戦闘が続く。
- `enterBattle` / `swappedOut` / `knockedOut` イベントをイベントログに記録する（「味方が戦闘不能になったら」「登場時」系のアシストに使う。§4.7）。

#### 行動順（確定）
攻撃フェーズは **英霊 → 前衛 1 → 前衛 2 → 後衛 1 → 後衛 2** の順に処理する。バースト連鎖（§8.4）もこの順で判定する。

#### ポジション（確定）
- 前衛と後衛に、行動上の違い（攻撃・アビリティ・バーストの可否）はない。
- ただし、**スキル効果がポジションによって変わる**ことがある（「前衛にいるとき〇〇」「後衛の味方に△△」など）。
- 各キャラの状態にポジション（`hero` / `front` / `back` / `sub`）と枠番号を持たせる。
- 入れ替えでサブが入った場合、**倒れたキャラのポジションと枠番号を引き継ぐ**。ポジション依存の効果はその時点から入れ替え後のキャラに適用される。

### 4.5 キャラクターの瞬間状態
キャラが直接持つ状態は次のものだけとする。
- HP 割合（§4.11）
- バーストゲージ
- バフ／デバフ／状態異常のリスト（効果・枠・効果量・持続・付与されたフェーズ）
- アビリティごとの CT
- トークン：種類ごとの所持数
- ポジションと枠番号（§4.4）

アビ別・色別の使用回数、アシストの発動回数などの**回数はすべてイベントログから求める**（§4.7）。状態として二重に持たない（§3-3 と同じ考え方）。

### 4.6 フィールド状態（戦闘全体で共有）
キャラ個別ではなく戦闘全体で持つ状態。
- ターン数
- 敵の属性（クエスト設定として入力。§4.8 の相性判定と、「有利属性なら」などの条件に使う）
- **イベントログ**：戦闘中に起きたイベントをすべて記録する（§4.7）
- 敵 CT（表示する場合）
- **敵のデバフのリスト**（効果・枠・効果量・持続）。重複ルールは §7.1。敵に付いたデバフは、付与したキャラが交代・戦闘不能になっても残る（交代戦術で「デバフを撒いてからサブのアタッカーと交代する」使い方があるため）。

### 4.7 イベントログとカウンター
属性別・攻撃区分別などのカウンターは、**固定のフィールド変数としては持たず、イベントログへの集計クエリとして求める**。

理由：アシストの条件は「雷属性 × アビリティダメージ」「赤アビの使用」「特定キャラの通常攻撃」など、数える軸の組み合わせがキャラごとに異なる。軸ごとに変数を用意すると、新キャラのたびにフィールド変数が増える。

各イベントは次の項目を持つ。

| 項目 | 例 |
|---|---|
| 通し番号 | ログ内の順番（§4.7 の「その時点まで」の判定に使う） |
| ターン・フェーズ | 3 / `action`（フェーズは `turnStart` / `action` / `attack` / `enemy` / `turnEnd` のいずれか。§5 の 0・1・3・4・5 に対応。選択フェーズは操作だけでイベントを生まない） |
| 種類 | 下のイベント一覧のいずれか |
| 発生源キャラ | `eve` |
| 発生源キャラの属性（`sourceElement`） | `thunder`（イベントを起こしたキャラの属性。すべてのイベントが持つ） |
| ダメージの属性（`element`。`damage` のみ） | `thunder`（指定がなければ発生源キャラの属性、効果で指定した場合はその属性。§10.2） |
| 攻撃区分（ダメージのみ） | `normal` / `ability` / `burst` |
| 色（アビ関連のみ） | `red` |
| 発生源の種類 | ability / assist / burst / normalAttack / eidolon / manual（手入力） |

#### イベント一覧（トリガー名と共通）
**イベントの種類名とアシストのトリガー名は同じものを使う**（別名を作らない）。新しいイベントを追加したら、この表と Zod スキーマを同時に更新する。

| イベント | 発生するとき | 主な追加項目 |
|---|---|---|
| `battleStart` | 戦闘開始時（1 ターン目のターン開始処理の前） | — |
| `turnStart` | ターン開始処理 | — |
| `turnEnd` | ターンエンド処理（§5-5-3） | — |
| `abilityUsed` | アビリティの**使用**（プレイヤーの操作でアビを使った） | アビ ID、色 |
| `abilityActivated` | アビリティの**発動**（アビの効果が実行された。使用したときと、バースト・アビ・アシストの効果で発動したとき） | アビ ID、色、経路 `route`（`use` / `effect`） |
| `normalAttack` | 通常攻撃 1 行動 | `combo`（連撃数）、発生元（攻撃フェーズ／アビ効果） |
| `burst` | バースト 1 回 | 消費ゲージ量、`source`（`attackPhase` / `ability`） |
| `damage` | ダメージ 1 ヒット | 攻撃区分、ダメージの属性 |
| `damaged` | 被弾（手入力） | 回数 |
| `heal` | 回復 | 対象 |
| `gaugeChanged` | ゲージの増減 | 対象、増減量、手段（`normalAttack` / `chain` / `effect` / `turnEnd` / `damaged`） |
| `buffApplied` / `buffOverwritten` / `buffMissed` / `buffConsumed` / `buffExpired` / `buffRemoved` | バフ・デバフ・状態異常の付与・上書き・MISS・消費・期限切れ・解除 | 枠、効果量、`polarity`、累積数（累積型のみ。§7.1） |
| `assistTriggered` | アシストの発動 | アシスト ID（回数上限の判定に使う） |
| `enterBattle` | キャラがメインに出た（戦闘開始時のメインを除く） | 経路 `via`（`replenish`：補充／`swap`：交代） |
| `swappedOut` | 交代でサブに下がった | — |
| `knockedOut` | 戦闘不能（手入力） | — |
| `tokenAdded` | トークンの付与（上限で破棄された分は記録しない） | トークン名 `token`、付与した数 `amount` |
| `tokenConsumed` | トークンの消費（コスト・`consumeToken` の両方） | トークン名 `token`、消費した数 `amount` |

- `tokenAdded`・`tokenConsumed` の発生源キャラは**トークンの持ち主**とする（フィルターの `source: "self"` が「自分のトークン」を指すように）。

#### 条件の評価時点（確定）
キューに積まれたイベントを 1 件ずつ処理するとき（§6.1-4）、条件は次のように評価する。
- **回数の条件（`count`）は、そのイベントの時点までのログ**で数える。つまり、処理中のイベントの通し番号以下のイベントだけを数える。
  - 例：10 ヒットのアビで `damage` が 10 件積まれた場合、5 件目の `damage` を処理するときの「今ターンのアビダメージ回数」は 5（10 ではない）。そのため「5 回ごと」のアシストは 5 件目と 10 件目でだけ発動する。
- **状態の条件**（ゲージ、HP、バフの有無、トークン、ポジションなど）は、**判定する瞬間の現在の値**で見る。
- 「そのイベントの時点まで」には、そのタイミングの処理を始めてから記録されたイベント（同じタイミングで先に発動したアシストの `assistTriggered`・効果が生んだイベント）も含める。数えないのは、キューに積まれてまだ処理していないイベント（10 ヒットのアビの 6〜10 件目の `damage` など）だけ。
- アシストの回数上限（`limit.perTurn` など）は、`assistTriggered` イベントを数えて判定する。
- `assistTriggered` はアシストの効果を処理する**前**に記録する。そのため、アシストの効果の中で数える「このアシストの発動回数」は今回を含む（「5 の倍数回目の発動時」などに使う）。
- **個数を数える `sum`**：`count` に `"sum": "amount"` を付けると、件数ではなくイベントの `amount` の合計を数える。「反想を 10 消費」は `tokenConsumed` 1 件で `amount: 10` なので、「消費した数」「獲得した数」は `sum` で数える。

条件からは次のように参照する。
```json
{ "count": {
    "event": "damage",
    "filter": { "element": "thunder", "category": "ability" },
    "scope": "turn",
    "gte": 15
} }
```
- `scope`：`turn`（今ターン）/ `battle`（戦闘全体）
- `filter` は上表のどの項目でも絞り込める。
  - 「雷属性のキャラが赤アビを使った回数」は `{ "event": "abilityUsed", "filter": { "sourceElement": "thunder", "color": "red" } }`（アビには属性がないため。§4.1）。
  - 「雷属性のダメージの回数」は `{ "event": "damage", "filter": { "element": "thunder" } }`。全属性ダメージの雷の 1 ヒットなど、雷以外のキャラが出した雷ダメージも数える。
  - 「雷属性のキャラが与えたダメージ」なら `sourceElement` で絞る。説明文がどちらを指すか読み分けること。

#### 行動単位とヒット単位（確定）
多段ヒットや連撃は、**何を数えるか**で「1 行動 = 1 回」か「1 ヒット = 1 回」かが変わる。そのため、行動を表すイベントと、ヒットを表すイベントを分けて記録する。

| イベント | 単位 | 1 回の三段攻撃で | 10 ヒットのアビで | 使う場面 |
|---|---|---|---|---|
| `normalAttack` | 行動 | 1 件（`combo: 3` を持つ） | — | 「通常攻撃を〇回行った時」 |
| `abilityUsed` | 行動 | — | 1 件 | 「アビリティを〇回使用した時」 |
| `damage` | **ヒット** | 3 件（区分 `normal`） | 10 件（区分 `ability`） | 「〇回ダメージを与えるごとに」、敵の「〇回攻撃でバリア解除」 |

#### アビの「使用」と「発動」（確定）
説明文の「使用」と「発動」は別物として数える。
| | 使用（`abilityUsed`） | 発動（`abilityActivated`） |
|---|---|---|
| プレイヤーがアビを使う | 1 件 | 1 件 |
| バースト・アビ・アシストの効果でアビが発動する（`activateAbility`。§10.2） | **記録しない** | 1 件 |
- 「アビを〇回使用したら」は `abilityUsed`、「〇回目の発動では」は `abilityActivated` で数える。例：イヴのバーストで発動したアビ 1 は、アビ 1 の発動回数には入るが、使用回数（「赤アビを 5 回使用」など）には入らない（`CHARACTER.md`）。
- データを入力するときは、説明文が「使用」と「発動」のどちらを書いているかを読み分けること。

- **ダメージを与えるアビは「アビ使用」と「アビダメージ」の両方に数える**（確定）。上表のとおり、`abilityUsed` 1 件と `damage`（区分 `ability`）をヒット数ぶん記録する。
- バーストの多段演出の扱い（ヒット数ぶん数えるか、1 回か）は未確定（§11）。参考：ダメージプラスはバーストでは合計に 1 回だけ加算される。

条件の書き方の例：
```json
{ "count": { "event": "normalAttack", "scope": "turn", "gte": 3 } }
{ "count": { "event": "damage", "filter": { "category": "ability" }, "scope": "turn", "gte": 15 } }
```
- 実装では、モンテカルロ実行の速度のために、よく使われる組み合わせを索引付きカウンターとしてキャッシュしてよい。ただし**正はイベントログ**とする。

### 4.8 属性相性
初期版はダメージ量を計算しないため、相性は**表示と条件判定**に使う。倍率はダメージ計算を追加するときのために記録しておく。

#### 相性の種類と倍率（提供情報。実機確認は未）
| 相性 | 与ダメージ倍率 | 被ダメージ倍率 |
|---|---|---|
| 有利 | 1.48 | 0.75 |
| 等倍（同属性・無関係） | 1.00 | 1.00 |
| 不利 | 0.75 | 1.48 |

#### 有利・不利の関係
- **4 属性**：火・水・風・雷の間に有利・不利の関係がある。
  - 提供情報で明記されているのは「火 → 風が有利」「火 → 水が不利」。
  - 4 属性の循環は **火 → 風 → 雷 → 水 → 火** と推定（各属性が次の属性に有利）。**未確認**（§11）。
- **光・闇（プレイヤー有利の仕様）**：プレイヤー側の光が敵の闇を、プレイヤー側の闇が敵の光を攻撃するとき、プレイヤーは**一方的に**有利補正を受ける（与ダメ 1.48、被ダメ 0.75）。敵側が 1.48 倍になることはない。
- **幻属性の敵**：プレイヤー側の光・闇は有利（1.48）、火・水・風・雷は等倍（1.00）。

#### 判定関数
`affinity(attackerElement, defenderElement, side)` は `advantage` / `neutral` / `disadvantage` を返す。`side`（`player` / `enemy`）で光・闇の非対称性を扱う。相性の表は `src/engine/` に定数として 1 か所だけ置くこと。

#### ダメージ計算を追加する場合の参考（§4.8）
- 有利属性で「急所」（ウェポンスキル等）が発動すると、さらに 1.2 倍が乗算される。
- 既存のダメージ計算ツールとして「神姫計算機Re」がある。ダメージ計算をスコープに入れる場合は、計算式の検証に使えるか確認すること。

### 4.9 ユーザー補正（アクセサリなど）
アクセサリ（および必要ならウェポンスキルなど）は**キャラデータとしては持たず、チャートごとにユーザーが手入力するオプション**とする。

理由：所持状況や強化度合いがユーザーごとに違い、共通データにすると組み合わせが膨大になるため。

- 補正はチャートのデータに含め、共有 URL や JSON 出力にも含める（他人のチャートを再現できるように）。
- 入力は 2 段構え：
  1. **よく使う項目のフォーム**：キャラごとの「開始時ゲージ」「通常攻撃のゲージ上昇量 +%」「2 段攻撃率・3 段攻撃率」（§9）など。
  2. **詳細入力**：効果 DSL（§10）のトリガー付き効果を、キャラ単位で自由に追加できる（例：`battleStart` で `gaugeUp` 20）。
- 内部では、どちらもキャラに付与される「ユーザー定義アシスト」として同じ仕組みで処理する。
- **キャラのオプション**：キャラ定義の `options`（専用武器の有無など。§4.2）を、チャートごと・キャラごとに選ぶ。未選択なら各オプションの `default` を使う。
- **ユーザー定義のバースト**：`burst.userDefined: true` のキャラ（英霊のみ。§4.2）は、バーストの効果をチャートごとに詳細入力（効果 DSL）で上書きできる。上書きしないときはキャラ定義の `burst.effects`（既定の効果）を使う。`burst.effects` もないときは、バースト区分の自属性ダメージ 1 ヒットだけを持つものとして扱い（確定）、チャート上に「バーストの効果が未設定」と表示する。初期版は上書きの入力を作らず、既定の効果で固定する（§15.3）。
- 項目の一覧は、実際に使われるアクセサリ効果を確認して決める（§11）。

### 4.10 チャートデータの形式
保存・共有・Undo/Redo・テストケースの単位になるデータ（§3-7）。これ以外はすべてエンジンが再計算する派生データとする。

- **ユーザーはこの形式を直接編集しない**。プレイ画面（§14.0）での操作が、操作の記録として追記される。編成・ユーザー補正・設定は、それぞれの設定画面で編集する。
- 操作の記録は「プレイヤーがゲームで行う操作」をそのまま並べたものにする（アビ使用、バースト発動の切り替え、攻撃ボタン、敵フェーズの手入力）。エンジンはこれを先頭から再生して各時点の状態を求める。
- 操作の記録は **git のブランチのような木構造**で持つ（§4.12）。

| 項目 | 内容 |
|---|---|
| `version` | チャートデータの形式のバージョン（形式を変えたときに古いデータを変換するため） |
| `party` | 編成：英霊、前衛 1・2、後衛 1・2、サブ 1・2 のキャラ ID（§4.4） |
| `quest` | クエスト設定：敵の属性（§4.6）、敵 CT の最大値（表示する場合） |
| `nodes` | 操作の記録の木。1 ノード = 1 操作（下記、§4.12） |
| `branches` | ブランチの一覧：名前、先端のノード ID、メモ（§4.12） |
| `currentBranch` | 今プレイ画面で表示しているブランチ |
| `corrections` | ユーザー補正：キャラごとの開始時ゲージ、ゲージ上昇量 +%、2 段・3 段攻撃率、詳細入力の効果、ユーザー定義のバースト、キャラのオプション（§4.9、§9）。全ブランチ共通 |
| `settings` | 仮置き仕様の切り替え（`assistReentry`、`assistEventOrder`、`assistTiming` など）。**チャートごとに持つ**（共有したチャートが他の人の環境でも同じ結果になるように）。全ブランチ共通 |

`nodes` の 1 要素（1 操作）：
| 項目 | 内容 |
|---|---|
| `id` | ノード ID |
| `parent` | 親ノードの ID（最初の操作は `null`） |
| `op` | 操作の種類と内容：`useAbility`（キャラ ID・アビ ID・`chosenAlly`）、`setBurst`（パーティ全体の発動 / 温存）、`attack`（攻撃フェーズの実行。`comboOverride` を含む）、`enemyPhase`（手入力イベント：被弾回数、戦闘不能、敵のデバフ付与、HP 割合など）、`nextTurn` |
| `memo` | 自由記述のメモ（任意） |

- ターンごとの表（§14.1）は、ブランチの先端から根までの操作をたどり、`nextTurn` で区切って組み立てる派生データとする。
- 読み込み時（localStorage・JSON・共有 URL）は**必ず Zod で検証**し、通らないデータは読み込まない。詳細入力の効果も DSL の部品名だけで書かれていることを確認する（§3-4）。
- 共有 URL では、チャートデータを圧縮（lz-string など）してから URL に入れる。長すぎて URL に入らない場合は JSON 出力を案内する。

### 4.11 HP の扱い
HP の増減はスコープ外だが、HP を条件にする効果（`hpRate`、旺盛・反逆など）があるため、次のように扱う。
- 既定では**全員の HP を常に 100% とみなす**。
- ユーザーは手入力イベント（§4.10）で「T3 の行動フェーズ開始時に前衛 1 の HP は 40%」のように HP 割合を指定できる。指定した値は、次に指定するまでそのまま続く。
- `heal` 効果はイベントの記録だけ行い、HP 割合は変えない（回復量を計算しないため）。
- 戦闘不能は HP 0% ではなく、`knockedOut` の手入力イベントで表す（§4.4）。

### 4.12 行動分岐（ブランチ）
チャートの別案を、git のブランチのように枝分かれさせて持てるようにする。

**仕組み**
- 操作の記録は木構造で、各ブランチは「先端のノード」を指す名前付きの印にすぎない。ブランチの中身は、先端から根までたどった操作の列。
- 途中の時点まで共通の操作は、ブランチ同士で**共有する**（コピーしない）。
- 過去の時点に戻って違う操作をすると、その時点から**新しいブランチが自動で作られる**。元のブランチは消えずに残る（記録の破棄はしない）。
  - 例：「本線」の T3 に戻り、イヴのアビ 2 の代わりにアビ 3 を使う → T3 の途中から「本線-2」が分岐する。T1〜T3 の途中までは本線と共有する。
- ブランチには名前を付けられる（例：「本線」「T3 でアビ 3 を先に使う案」）。削除もできる。削除されたブランチだけが使っていたノードは消す。
- マージ（ブランチを合流させる）はしない。チャートの案は「どちらかを選ぶ」ものなので不要。

**エンジンとの関係**
- エンジンは、ブランチの根から先端まで操作を再生するだけで、ブランチの仕組みを知らなくてよい（§3-1）。
- 切り替えを速くするため、ノードごとの再計算結果をキャッシュしてよい（派生データ。チャートデータには含めない）。共通部分の再計算はブランチ間で使い回せる。

**ブランチの比較**
- ブランチの一覧に、ブランチごとの成功確率（§9）、最後のターン数、フルバーストの回数、警告の数を並べて表示する。成功確率はブランチごとに計算する。
- 2 つのブランチを選ぶと、分岐した時点と、そこから先の操作の違いをターン表で並べて表示する。

**共有**
- JSON 出力は全ブランチを含める。
- 共有 URL は長くなりやすいので、既定では**今のブランチだけ**を含める（全ブランチを含めるかを選べる）。URL に入らない場合は JSON 出力を案内する（§4.10）。

## 5. ターン進行（確定）

1 ターン = 味方の行動 + 敵の行動。

0. **ターン開始処理**：`turnStart` イベントを発行し、「ターン開始時」のアシストを処理する。1 ターン目だけは、その前に `battleStart` イベントを発行する。
1. **行動フェーズ**：CT が 0 のアビリティを、好きな順・好きな回数で使う（1 ターン上限の範囲内）。条件を満たしたアシストはその場で発動する。
2. **選択フェーズ**：**パーティ全体で 1 つ**の「バースト発動 / 温存」を指定する（確定）。キャラごとの個別指定はできない。
   - 「発動」：攻撃フェーズで、自分の番にゲージが 100 以上のキャラは**全員**バーストする。
   - 「温存」：全員が通常攻撃をする（ゲージが 100 以上でもバーストしない）。
   - 指定はターンごとに切り替えられる。前のターンの指定を引き継ぐ。
   - 特定のキャラだけに撃たせたい場合、ゲームでは配置順の調整、単体ゲージ UP、ターンごとの切り替えで対応する。ツールもこの制約どおりに再現する。
3. **攻撃フェーズ**：攻撃ボタンで全員が**行動順に**攻撃する。
   - 各キャラの番で、パーティの指定が「発動」かつゲージ ≥ 100 ならバースト、それ以外は通常攻撃。
   - **バーストは通常攻撃の代わりに発動する**（確定）。バーストしたキャラは、その番に通常攻撃をしない（通常攻撃によるゲージ上昇・`normalAttack` イベント・通常攻撃ダメージも発生しない）。
   - バーストしたキャラは、自身を除く**未行動**の味方のゲージを +10 する（§8）。そのため処理順が結果に影響する。
4. **敵フェーズ**：敵が行動する（スコープ外。必要な影響は手入力イベント）。
5. **ターンエンド処理**（次のターンへ移行する瞬間）：
   1. スリップダメージ（毒・腐敗・熱狂など）。これによる戦闘不能は手入力イベント
   2. 戦闘不能になったメイン神姫の枠に、サブを補充する（§4.4）。敵フェーズとスリップダメージの両方による戦闘不能が対象
   3. `turnEnd` イベントを発行し、ターン終了時のゲージ上昇（奮励・鼓舞・熱狂など）と「ターン終了時」のアシストを処理する
   4. ターン制のバフ／デバフ／状態異常の残りターンを 1 減らし、0 のものを削除する。ただし**このターンの敵フェーズ中に付与されたものは減らさない**（§7）
   5. メインにいるキャラのアビリティの CT を 1 減らす（0 未満にはしない）。**サブで待機中のキャラは減らさない**（§4.4）

   > ⚠️ 順番は**仮置き**（§11）。確定しているのは「スリップダメージでの戦闘不能もターン終了時に補充される」こと。そのため補充はスリップダメージの後に置いた。補充されたキャラに 3〜5 が適用されるかは未確定。
   >
   > 「今ターンの使用回数」などのターン単位のカウンターは、イベントログをターン番号で絞り込んで求める（§4.7）ため、リセット処理は不要。

## 6. CT（確定）

- 戦闘開始時：全アビリティ CT = 0（使用可能）。
- 使用時：CT を最大値に戻す。
- ターンエンド処理：CT を 1 減らす。
- アシストなどで CT が 0 になれば、**同じターン中に再使用できる**（1 ターン上限の範囲内）。
- 例：CT3 のアビを T1 に使用 → T1 終了で 2 → T2 終了で 1 → T3 終了で 0 → **T4 に再使用可**。

### アビリティの使用判定
すべて満たすとき使用可能：
- CT が 0
- 今ターン使用回数 < 1 ターン上限（上限があるアビのみ）
- 戦闘中使用回数 < 戦闘上限（上限があるアビのみ）
- コスト（バースト、トークンなど）を支払える
- 固有の使用条件を満たす

### 使用時の処理
1. コストを支払う
2. CT を最大値に戻す
3. `abilityUsed` と `abilityActivated`（経路 `use`）をイベントログに記録する（使用回数・発動回数・色別の回数は、このログを集計して求める。§4.7）
4. 効果を順に処理する
5. 記録したイベントのアシストを判定する。複数のアシストが条件を満たした場合は §6.1 の順で処理する。

- `changeCT` で CT を減らす場合、0 未満にはしない。
- 手順 2（CT を最大値に戻す）は効果の処理（手順 4）より前に行う。そのため、効果の中で自分の CT を 0 にする（即リキャ）と、その結果が残る。

### コスト（条件付きコスト）
コストは配列で書き、各要素に `when`（条件）を付けられる。`when` を満たす要素のコストだけを支払う。支払えないときは使用不可。
```json
"cost": [
  { "gauge": 20, "when": { "useCount": { "ability": "self", "scope": "turn", "gte": 1 } } },
  { "token": { "name": "雷光", "amount": 3 } }
]
```
- コストの種類：`gauge`（バーストゲージ）、`token`（固有トークン）、`hpRate`（HP 割合。§4.11）。
- **コスト・使用条件の `when` は、使う前に評価する**。このとき今回の使用はまだイベントログにないので、`useCount` は**これまでの使用回数**になる（今回を含まない）。効果の中の `useCount` は `abilityUsed` を記録した後（手順 3 の後）に評価するので、**今回を含む**。どちらも「評価する時点のログで数える」（§4.7）という同じ原則による。
- 使用条件（`usable`）も条件（cond）で書ける。コストとは別に「この状態のときだけ使える」を表す。

### 即リキャ（CT を 0 にする効果）
「即リキャ」には種類がある。専用の項目は作らず、**効果の部品の組み合わせで書く**。
| 種類 | 書き方 |
|---|---|
| 使った直後に自分の CT が 0 になり、2 回目以降の使用にコストがかかる（イヴのアビ 2） | 自分の CT を 0 にする `changeCT`（`setTo: 0`）を `useCount` の条件付きで ＋ `useCount` の条件付きコスト（`CHARACTER.md` のイヴ） |
| コストを払うと CT が 0 になる | 効果の中で `consumeToken` / `gaugeDown` の後に `changeCT`（`setTo: 0`）。払えるかを `if` で確かめる |
| 条件を満たすと CT が 0 になる | `if` の条件（トークン数、使用回数、HP など）で `changeCT`（`setTo: 0`） |
| 他のキャラやアシストが CT を減らす | `changeCT`（`amount: -1` など。イヴのアシスト 1） |
- 種類によっては、プレイヤーがコストを払うかどうかを選べる可能性がある。その場合の扱いは未確定（§11）。

**省略形 `recast`（条件付きの即リキャ）**
条件付きの即リキャは多くのアビで使われるため、データ入力の手間を減らす省略形を用意する。省略形は**読み込み時に上の部品の組み合わせへ展開**し、エンジンは展開後の部品だけを扱う（エンジンに即リキャ専用の処理を持たせない）。
```json
{ "type": "recast",
  "when": { "useCount": { "ability": "self", "scope": "turn", "lte": 2 } } }
```
- `when`：CT を 0 に戻す条件（回数上限・トークン・ゲージなど、§10.1 の条件をそのまま書ける）。
- 展開結果：`if when then [changeCT（self、setTo 0）]`。
- 即リキャにかかるコストは、アビの `cost`（条件付きコスト）に書く。イヴのアビ 2 のように「そのターンの 2 回目以降はコストがかかる」なら `useCount` で条件を書く（`CHARACTER.md` のイヴ）。
- 「即リキャで使えるようになった次の 1 回だけコストがかかる」種類が見つかった場合は、省略形に `nextCost` を追加し、即リキャ状態（`addStatus`、1 ターン）と「状態があればコスト」で展開する。
- 展開の処理と、展開前後が同じ挙動になることのテストを用意する。新しい種類の即リキャが見つかって省略形で書けない場合は、部品の組み合わせで直接書く。

**アシストの判定タイミング**（⚠️ 仮置き。クライアントの見立て「一旦これで」。実機未確認）
- アビの**効果をすべて処理した後**に、そのアビで生じたイベント（`abilityUsed`、ヒットごとの `damage`、ゲージ変化など）のアシストをまとめて判定する。
- 効果の途中（例：ダメージを出した直後、ゲージ +20 の前）では判定しない。そのため、アシストの条件は**アビの全効果が反映された後の状態**を見る。
- 実装：アビの効果処理中に生じたイベントはキュー（§6.1-4）に積むだけにし、効果がすべて終わってからキューを処理する。§6.1-4 の「後回し」と同じ仕組みで実現できる。
- 設定 `assistTiming: "afterAbility" | "perEffect"` で切り替えられるようにする（既定は `"afterAbility"`）。

### 6.1 アシストの処理順（1・2 は確定、3・4 は仮置き）

同じタイミング（「ターン終了時」「特定回数攻撃時」「アビ使用時」など、1 つのイベント）で複数のアシストが条件を満たした場合：

1. **編成順**（左から右）に処理する：英霊 → メイン 1 → メイン 2 → メイン 3 → メイン 4 → サブ 1 → サブ 2。
   - サブは `activeIn` が `sub` / `both` のアシストのみ対象（§4.4）。
   - 入れ替え後は、そのキャラが今いる枠の順番を使う（§4.4 補充されたキャラは枠を引き継ぐ）。
2. 同じキャラが複数のアシストを持つ場合は、**キャラ詳細画面の上から順**（アシスト 1 → アシスト 2 → …）。キャラ定義の `assists` 配列の並びをこの順にすること。
3. ⚠️ **仮置き（クライアントの見立て。実機未確認）**：後ろのキャラのアシストによって前のキャラのアシストの条件が満たされた場合、**同じタイミング内で前に戻って発動する**。
   - 提供情報（「戻らない」）とは逆。クライアントの見立てを優先して仮置きとし、実機で確認すること（§11）。
   - 例：英霊のアシスト A（ゲージ 100 以上なら〇〇）は最初の判定ではゲージ 90 で不発。その後メイン 3 のアシスト B で英霊のゲージが 110 になったら、同じタイミング内で A が発動する。

**再評価の手順（仮置き）**
1. 対象のアシストを編成順に並べ、先頭から判定する。
2. どれかが発動したら、**そのタイミングでまだ発動していないアシスト**を、先頭から判定し直す。
3. 一巡して新たに発動したものがなければ終了。

- **1 つのアシストは、1 つのタイミングで最大 1 回まで**発動する（発動済みのものは再評価しない）。これがないと「ゲージ 100 以上なら」のような条件が満たされ続けて無限に発動するため。この解釈も実機で確認すること（§11）。
- アシスト自身の回数上限（イヴのアシスト 1 の「1 ターン 10 回まで」など）は別途適用する。

実装：
- 戻るかどうかは**設定で切り替えられるようにする**（`assistReentry: true` を既定）。`false` にすると、先頭から 1 回ずつ判定して終わる（提供情報の挙動）。コードには `// TODO(spec): §6.1-3 連鎖は実機未確認` を付ける。
- 「1 タイミング 1 回まで」のおかげで、再評価は最大でもアシストの数だけで止まる。それでも想定外の組み合わせに備えて §3-8 の安全装置を残す。

4. ⚠️ **仮置き（クライアントの見立て。実機未確認）**：アシストの効果が新しいイベント（ダメージ、ゲージ変化、バフ付与など）を生んだ場合、**そのイベントでも別のアシストが発動しうる**。ただし**後回し**で処理する。
   - アシストの効果によるダメージなども、イベントログのカウンター（§4.7）に数える。例：イヴのアシスト 2 のアビダメージは、「アビダメージを〇回与えるごとに」の回数に入る。
   - 今のタイミングのアシストをすべて処理し終えてから（3 の再評価も含む）、新しく生まれたイベントのタイミングを処理する。割り込みはしない。

**イベントキューによる実装（仮置き）**
- エンジンはイベントを**キュー（先入れ先出し）**で処理する。
- 1 つのイベントを取り出し、そのタイミングのアシストを §6.1 の 1〜3 で処理する。アシストの効果が生んだイベントはキューの末尾に積むだけで、その場では処理しない。
- キューが空になったら、プレイヤーの操作（次のアビ使用など）に戻る。
- 「割り込み」に切り替えられるよう、設定 `assistEventOrder: "queue" | "interrupt"` を持たせる（既定は `"queue"`）。
- アシスト A のダメージで B が発動し、B のダメージで A が発動する、という往復は「1 タイミング 1 回まで」では止まらない（タイミングが別のため）。アシスト自身の回数上限で止まることが多いが、上限のない組み合わせに備えて §3-8 の安全装置で止める。
- プレイヤーの行動をまたぐ連鎖（アシストで CT が 0 → プレイヤーが再使用 → 次のアシスト判定）は、プレイヤーの操作ごとに区切られるので無限にはならない。
- イヴのアシスト1（CT-1）でアビが再使用可能になっても、再使用はプレイヤーの次の操作として扱い、自動では使わない。

## 7. バフ／デバフ／状態異常

持続の種類は 3 つ。

| 種類 | 減るタイミング | 例 |
|---|---|---|
| ターン制 | ターンエンド処理 | 「3 ターンの間、攻撃力 UP」 |
| 回数制 | 対象イベント発生の瞬間（ターン経過では減らない） | 「〇回攻撃まで」「〇回被弾まで」 |
| 永続 | 解除されるまで減らない。`"duration": { "permanent": true }` で書く（確定） | ターン数表記なし |

- 回数制の**攻撃バフ**（「次の攻撃 1 回のみ UP」など）は**行動単位**で消費する（確定）。三段攻撃なら 3 発すべてに乗ったうえで 1 回分消費、多段アビも 1 アビ全体に乗って 1 回分消費。
- 「〇回被弾まで」などの防御系の回数制バフが、多段の敵攻撃でヒット単位に減るかは未確定（§11）。

- 味方の行動中に付与された 1 ターン効果は、そのターンの味方攻撃と直後の敵攻撃まで持続し、ターンエンド処理で消える。
- 敵の行動中に付与された 1 ターン効果は、次の味方ターンとその次の敵攻撃まで持続する。
  - 実装：効果に「付与されたフェーズ」を記録し、**敵フェーズ中に付与された効果は、そのターンのターンエンド処理では残りターンを減らさない**（§5）。次のターンのターンエンド処理から減らし始める。

### 7.1 重複ルール（バフ・デバフ共通。確定）
バフもデバフも**枠（系統）**に属する。ゲーム内に公式の枠表記はなく、有志の検証による分類を使う。重複のルールはバフとデバフで共通。同じ枠で付与できなかったとき、ゲーム内ではバフは「CANCEL」、デバフは「MISS」と表示される（2026-11-11 クライアント情報）。ツール上はどちらも `buffMissed` イベント（`polarity` で区別）として扱う。本ファイルの「MISS」は両方を指す。

| 状況 | 結果 |
|---|---|
| 異なる枠 | 共存する（ダメージ計算では基本的に乗算） |
| 同じ枠・新しい方が効果量が大きい | 上書き（新しい効果量・持続に置き換わる） |
| 同じ枠・新しい方が効果量が小さい | **CANCEL**（バフ）／**MISS**（デバフ）（付与されない。既存のバフはそのまま） |
| 同じ枠・効果量が同じ | 上書き（**持続も新しい方に置き換わる**。持続が短くなることがある）。デバフで同じかは仮置き（§11） |

- 小さい効果で MISS になった場合、既存の効果の**持続も更新されない**（確定）。
- **状態（`addStatus`）の付け直し**：同じ名前の状態がすでに付いているときに付け直すと、残りの持続に足さず、**新しい持続に置き換える**（確定。シャイターンのリミッター解除）。状態は効果量を持たないので MISS にはならない。

#### 累積型のバフ（「累積可」）
説明文に「累積可」「累積する」とあるバフは、同じバフを重ねるたびに効果量が増える。例：イヴのアビ 2 のダメージ上限 UP（`CHARACTER.md`）。
- `addBuff` に `stack` を付けて書く。
  - `max`：累積の上限。上限がなければ `null`（不明の場合は `"unknown"`）。
  - `duration`：重ねたときの持続の扱い。
    - `"perStack"`：**1 段ごとに自分の持続を持ち、それぞれ別々に切れる**（確定した種類。イヴのアビ 2）。
    - `"refresh"`：重ねるたびに全体の持続を新しい方に更新する（存在は未確認。見つかったら使う）。
    - `"unknown"`：説明文から分からない。エンジンは `perStack` として扱い、チャート上に「累積の持続の扱いが不明」と表示する。
  ```json
  { "type": "addBuff", "target": "allAllies", "buff": "ダメージ上限UP", "slot": "dmgCapUp", "amount": null,
    "stack": { "max": null, "duration": "perStack" }, "duration": { "turns": 2 } }
  ```
- `perStack` の場合、1 段が切れるたびに `buffExpired` を記録し、残りの累積数を持たせる。ガントチャート（§14.2）では、段ごとの持続が分かるように描く。
- **同じバフ（`buff` 名が同じもの）がすでにあれば、上の表の上書き・MISS の判定をせず、累積数を 1 増やす**（確定：累積する）。合計の効果量は「1 回分の効果量 × 累積数」とする。`max` に達していたら累積数は増えない（この場合 MISS 扱いにするかは未確定 §11）。
- `buffApplied` イベントに累積後の累積数を記録する。ガントチャート（§14.2）では棒の中に累積数を表示する。
- 条件 `hasBuff` には累積数の比較（`stacks: { "gte": 3 }` など）を書けるようにする。
- ⚠️ 未確定（§11）：
  - `stack.duration` の種類は、`perStack` 以外に実在するか。説明文から判断できない場合は確認すること。
  - 同じ枠に別の（累積しない）バフがある場合の扱い。決まるまでは、累積型は**同じ `buff` 名のものとだけ**重なり、別のバフとは上の表のルールで、合計の効果量どうしを比べて判定する。
  - 合計の効果量が分からない（`amount: null`）場合は、§7.2 と同じく判定できない旨を表示する。

チャートツールとして重要なのは、ダメージ量ではなく次の 2 点。
- **MISS の検出**：付与したつもりのバフが入っていない。`buffMissed` イベントを記録し、チャート上で警告表示する。
- **持続の上書き**：同じ効果量で上書きすると持続が短くなりうる。「後のターンでバフが切れる」原因として警告表示する。

どちらも `hasBuff` 条件や回数制バフに影響するため、ダメージを計算しない初期版でも必ず実装する。

### 7.2 バフ枠の定義
- 枠の一覧はキャラデータとは別のデータ（`src/content/buffSlots.json`）として管理する。キャラ定義の `slot` は必ずこの一覧の ID を使い、新しい枠はこの一覧に足してから使う（キャラごとに ID を作ると、同じ枠の重複判定ができなくなるため）。現在の一覧は 3 体を入力したときに作った仮置き。
- `addBuff` 効果は `slot`（枠 ID）と `amount`（効果量）を持つ。重複判定はこの 2 つで行う。
- **効果量は実際の数値で持つ**（確定）。説明文が「大」「特大」などの段階表記でも、wiki などで調べた実数値（例：攻撃力 UP 大 = 30%）を入力する。将来のダメージ計算にもそのまま使う。
  - 単位は枠ごとに統一する（% の枠、固定値の枠など）。単位は枠データ（`buffSlots.json`）に持たせる。
  - 実数値が分からない場合は `amount: null` とし、出典が見つかり次第埋める。`null` のバフ同士・`null` と数値の比較では重複の結果を決めず、チャート上に「効果量が不明のため MISS・上書きを判定できない」と表示する（推測で判定しない）。
  - 実数値の出典（wiki のページなど）をキャラ定義の `source` 欄に残し、レビューで確認できるようにする。
- 発生源によって枠が分かれる場合は、別の枠として登録する（例：神姫のアビによる属性攻撃 UP と、幻獣による属性攻撃 UP は別枠で重複可能）。
- 枠ごとの合算方法（加算か乗算か）と上限は、ダメージ計算用の参考情報として枠データに持たせる。初期版のエンジンは使わない。

主な攻撃系の枠（提供情報）：
| 枠 | 備考 |
|---|---|
| 攻撃力 UP | 通常攻刃・アビリティ攻撃力 UP など |
| 属性攻撃 UP | 神姫のアビ由来と幻獣由来は別枠 |
| 旺盛（HP 50% 以上で攻撃 UP） | 武器単体上限 100%、武器 + アビ合計上限 200% |
| 反逆（HP が減るほど攻撃 UP） | 武器単体上限 150%、武器 + アビ合計上限 200% |
| 特殊攻撃 UP | |
| 通常攻撃ダメージ UP / 攻防ダメージ UP（ランページ・スレイヤーなど） | 上限 300% |
| 与ダメージ UP（白虎の召喚効果、アクセのタイムピースなど） | 被ダメ UP デバフや恐傷とも合算 |
| クリティカル / 会心 | 有利属性に対して 1.5 倍などの乗算 |

```json
{ "type": "addBuff", "target": "allAllies", "buff": "攻撃力UP", "slot": "atkUp", "amount": 30, "duration": { "turns": 3 } }
```
- 効果が乗る攻撃区分が決まっているバフ（「すべての攻撃区分で」「アビリティダメージのみ」など）は、`categories`（`normal` / `ability` / `burst` の配列）で書く。省略時は枠の既定に従う。初期版のエンジンは使わない（ダメージ計算用の参考情報）が、データには説明文どおりに残す。

主なデバフの枠（提供情報）：
| 枠 | 例 |
|---|---|
| A 枠（通常枠） | 一般的な単体・全体デバフアビ（アーマーブレイク系） |
| B 枠（特殊・両面枠） | 攻防同時ダウン、特定条件で付与されるデバフ |
| C 枠（召喚・幻獣枠） | 幻獣の召喚効果によるデバフ |
| 専用枠 | 特定のキャラの固有名称デバフ（「〇〇の呪い」など）。他と重複しやすい |
| 属性耐性ダウン | 防御力ダウンとは完全に別枠 |

- 攻撃力ダウン・防御力ダウンは、それぞれ上の A〜C 枠・専用枠に分かれる。枠データには `polarity: "buff" | "debuff"` を持たせ、`buffSlots.json` にバフとデバフの枠を一緒に登録する。
- デバフの付与は `addDebuff`（`addBuff` と同じ引数）で書く。
- 別枠のデバフは加算されるが、**合計の下限**がある（攻撃力・防御力ダウンは基本的に合計 50% まで。一部の専用枠などに例外あり）。下限はダメージ計算用の参考情報として枠データに持たせる。初期版では、合計が下限に達した状態でさらにデバフを付けた場合に「下限に達しているため効果なし」と表示する。

## 8. バーストゲージ

### 8.0 開始時のゲージ（確定）
- 戦闘開始時のゲージは基本 **0**。
- 開始時にゲージを持つ効果（アクセサリ・アシストなど）は、`battleStart` トリガーの `gaugeUp` か、ユーザー補正（§4.9）で表現する。

### 8.1 上限と発動条件（確定）
- 上限は通常 **100**。一部のキャラ・英霊は **200**（キャラ定義の `gaugeMax`）。
- ゲージ **≥ 100** でバースト発動可能（上限 200 のキャラも同じ）。
- 上限を超える上昇は上限で切り捨てる。

### 8.2 バースト時の消費（確定）
| 方式 | 挙動 | 例 |
|---|---|---|
| `subtract100`（既定） | 100 だけ消費し、余剰は残る。上限 200 なら 2 ターン連続バーストも可能 | 英霊「頼光」 |
| `consumeAll` | 溜まっているゲージをすべて消費する。消費量が多いほど威力・上限が上がる | ペルケレ、[夏夜の爆華]メタトロン |
| アビ効果による即時バースト（基本） | ゲージは **0 に戻る**（§10.2） | — |
| アビ効果による即時バースト（消費なし） | 元のゲージは減らない | [ずっといっしょ]ヘル |

- 見分け方：アシストアビリティやバースト説明文に「全消費」とあれば `consumeAll`、記載がなければ `subtract100`。
- `burst` イベントには**消費したゲージ量**を記録する（`consumeAll` の威力条件などで参照できるように）。

### 8.3 上昇手段
| 手段 | 量 | 状態 |
|---|---|---|
| 通常攻撃 | `10 × (1 + 上昇量アップ合計%) × 連撃数` | 確定（クライアント確認） |
| バースト連鎖 | 自身を除く**未行動**の味方に **+10 固定** | 確定 |
| ターン終了時効果（奮励・鼓舞・熱狂） | 効果ごと | 確定 |
| アビリティ・バースト・アシストの効果 | `gaugeUp` 効果で記述 | 確定（使用するだけで上がる共通量があるかは未確定） |
| 被ダメージ | 未確定 | 敵行動はスコープ外のため手入力イベント |
| アクセサリ・幻獣効果 | 効果ごと | 確定（アクセサリはユーザー補正 §4.9 で手入力） |

#### 通常攻撃のゲージ上昇（確定）
```
上昇量 = 10 × (1 + 上昇量アップ合計%) × 連撃数
```
- **連撃数を掛ける**（三段攻撃なら 30）。クライアントが確定。以前の「連撃数に関係なく 1 行動 +10」という情報は誤りとして扱う。
- 「三段攻撃時にゲージ UP」などの専用アシストは、これとは別にアシストとして記述する。

- 上昇量アップは、神姫のバフ、アビリティ、英霊のアシスト、アクセサリをすべて**合算**する（例：+50% なら 15 × 連撃数、+100% なら 20 × 連撃数）。

#### 上昇量アップが乗る手段・乗らない手段（確定）
上昇量アップは**受け手側**（ゲージが増えるキャラ）にかかっているものを使う。

| 手段 | 上昇量アップ | 例（受け手に +50%） |
|---|---|---|
| 通常攻撃 | **乗る** | 三段攻撃なら 15 × 3 = 45 |
| アビ・バースト・アシストの効果による `gaugeUp` | **乗る**（受け手の倍率で乗算） | 「味方全体のゲージ +20」→ +30 |
| バースト連鎖 | **乗らない**（常に +10 固定） | +10 |
| ターン終了時効果（奮励など） | 未確定（§11） | — |

- **`gaugeUp` の量は、説明文に記載がなければ +20**（確定。クライアント指示）。JSON では `amount` を省略して書き（エンジンは 20 として扱う）、記載がなかったことを**依頼者に伝える**（`CHARACTER_DATA_GUIDE.md` §5）。量が分かったら数字を書く。
- `gaugeUp` 効果は、対象ごとに受け手の上昇量アップを掛けて適用する。上昇量アップを無視して固定量で増やす効果が見つかった場合は、`gaugeUp` に `fixed: true` を追加して対応する。
- 連撃はゲージ、ヒット単位のカウント（§4.7）、「三段攻撃時」系のアシストに影響するため、成功確率の計算（§9）の確率要素として扱う。

#### ゲージが上がらない例外（確定）
止められる手段は効果ごとに違う。
- 「通常攻撃でバーストゲージが上昇しない」（一部のアタッカーのデメリット）
- 「通常攻撃・被弾以外でバーストゲージが上昇しない」（一部のキャラのデメリット）
- 敵の「バーストゲージ上昇無効」（帯電・封印系などのデバフ）

いずれも状態効果 `gaugeGainBlocked` として扱い、**止める手段を `sources` で指定する**。
```json
{ "type": "addStatus", "target": "self", "status": "gaugeGainBlocked", "sources": ["normalAttack"] }
{ "type": "addStatus", "target": "self", "status": "gaugeGainBlocked", "sources": ["chain", "effect", "turnEnd"] }
```
- `sources` の値：`normalAttack`（通常攻撃）、`damaged`（被弾）、`chain`（バースト連鎖）、`effect`（アビ・バースト・アシストの `gaugeUp`）、`turnEnd`（ターン終了時効果）、`all`。
- キャラ固有のデメリットは永続の効果として `battleStart` で付与し、敵のデバフは手入力イベントで付与する。
- 敵の「上昇無効」デバフが止める範囲（連鎖の +10 も止めるか）は未確定（§11）。決まるまでは `all` で仮置きする。

### 8.4 バースト連鎖（フルバースト）（確定）
- バーストしたキャラは、自身を除く**未行動**の味方全体のゲージを基本 +10 する。
- 行動順に「100・90・80・70・60」と並んでいれば、前のキャラのバーストで次のキャラが 100 に届き、全員が連続でバーストする（フルバースト）。
- このため攻撃フェーズは**行動順に 1 人ずつ**処理し、各キャラの番でゲージを判定する（§5）。
- 発動指定はパーティ全体で 1 つ（§5）なので、「誰がバーストするか」はゲージの状態で決まる。プレイ画面では、攻撃ボタンを押す前に「このまま攻撃すると誰がバーストするか」の予測を表示する。
- 成功確率の判定では、操作を記録したときにバーストしたキャラを「バーストする予定のキャラ」とみなす（§9）。
- **連鎖（+10）が起きるのは攻撃フェーズのバーストだけ**（確定）。アビ効果による即時バーストでは発生しない（§10.2）。

### 8.5 バーストリンク
- 同一ターンに複数キャラがバーストすると発動する（参加人数が多いほど強い）。初期版ではダメージは計算せず、**リンク人数を表示**する。
- アビ効果による即時バーストでは、複数キャラが同時にバーストしても**チェインバースト（バーストの追加ダメージ）は発生しない**（確定）。
  - 「チェインバースト」と「バーストリンク」が同じものかは未確定（§11）。同じなら、リンク人数は攻撃フェーズのバーストだけで数える。

## 9. 確率要素と成功確率

- 連撃（2 段・3 段攻撃）は確率で発生する。
- **通常表示**：最低保証（1 段）で計算する。ユーザーはターン・キャラ単位で連撃数を手動で上書きできる。
- **成功確率**：モンテカルロ法でチャートを多数回（既定 10,000 回）実行し、成功した割合を表示する。
  - 失敗したケースの原因（ターン・キャラ・行動）を集計して表示する。
- **「成功」の定義（確定）：厳格判定**。**記録した操作**（アビの使用、交代など）と、**記録したときのバーストの結果**がすべて再現できた場合だけを成功とする。
  - 「バーストする予定のキャラ」は、操作を記録したときの通常表示（連撃は 1 段、または `comboOverride` で指定した段数）でバーストしたキャラとする。発動指定はパーティ全体で 1 つのため（§5）、キャラごとの予定は記録時の結果から決める。
  - 計画どおりにいかない行動が出た時点で、その試行は**失敗として打ち切る**。失敗になるのは次の 2 種類だけ。
    - バーストする予定のキャラが、ゲージが届かず通常攻撃になった。
    - 使う予定のアビが使えなかった（CT・回数上限・コスト・条件不足、`chosenAlly` の相手がいない）。
  - **確定**：予定していないキャラがバーストした場合（連撃が多く出てゲージが早く溜まったなど）は、**失敗にせず続行する**。ゲージの状態が変わるので、その後の予定のバーストやアビが崩れれば、そこで失敗になる。予定外のバーストの回数は集計して表示する。
  - **MISS や持続の上書き、デバフの下限到達は失敗にしない**。これらは乱数に関係なく毎回起こるため、失敗にすると成功確率が常に 0% になってしまう。チャート上の警告（§7.1、§14）として表示する。
  - 打ち切った位置（ターン・キャラ・行動）と原因を記録し、失敗原因の集計に使う。
  - 将来の拡張：崩れても最後まで実行し、ユーザーが指定した目標（例：T5 に 4 人フルバースト）を満たしたかで判定する「続行判定」を追加できるよう、判定部分は差し替え可能な関数にしておく。
- **連撃率データ（確定）：ユーザー補正で手入力**（§4.9）。チャートごと・キャラごとに、2 段攻撃率と 3 段攻撃率をユーザーが入力する。
  - 理由：連撃率は武器スキルやアクセサリで大きく変わり、ユーザーごとの差が大きいため。
  - 未入力のキャラは連撃なし（常に 1 段）として扱い、成功確率の画面で「連撃率が未入力のキャラがいる」と表示する。
  - 連撃率はチャートデータに含め、共有 URL・JSON 出力にも含める。
  - 将来の拡張：キャラ定義に基礎の連撃率を持たせ、ユーザー入力で上書きする形に広げられるよう、連撃率の取得は 1 か所の関数にまとめておく。
- アビ効果で連撃率を上げるバフの扱いは未確定（§11）。
- 「〇%で発動」する効果も同じ乱数注入の仕組みで扱う。

## 10. 効果記述（DSL）

アビリティ・アシスト・バーストの効果は、**エンジンに登録された部品の組み合わせ**で記述する。

### 10.1 部品の種類
| 部品 | 役割 | 例 |
|---|---|---|
| 効果（effect） | 実処理 | `damage`, `performAttack`, `addStatus`（`gaugeGainBlocked` など、効果量を持たない状態効果）, `removeStatus`, `heal`, `addBuff`, `addDebuff`, `removeDebuff`, `gaugeUp`, `gaugeDown`, `changeCT`, `addToken`, `consumeToken`, `swapWithSub`, `retire`, `activateAbility`（アビを発動させる。§10.2）, `repeat`（繰り返し）, `useEffects`（共有の効果の参照。読み込み時に展開） |
| 対象（target） | 誰に効くか | `self`, `allAllies`, `alliesWhere`（属性・ポジションなどで絞り込み）, `chosenAlly`（プレイヤーが選ぶ味方 1 体。§10.2）, `enemy`（敵単体）, `allEnemies`（敵全体）, `randomEnemy`（敵ランダム）。§10.2 |
| 条件（cond） | いつ効くか | `useCount`, `token`, `hpRate`（§4.11）, `hasBuff`, `hasDebuff`, `hasStatus`, `gauge`, `turnCount`, `element`, `position`, `count`（イベントログ集計 §4.7）, `trigger`（発動させたイベントの項目。§10.2）, `option`（ユーザーが選んだキャラのオプション。§4.2） |
| 数値（value） | 回数などから数値を求める（ヒット数など、数値を書く欄に使う。§10.2） | `useCount`, `count`, `token`。`mul` / `add` / `min` / `max` で計算できる |
| 論理 | 条件の組み合わせ | `and`, `or`, `not` |
| 分岐 | 効果の切り替え | `if`（then / else）, `switch`（cases / default） |
| トリガー | アシストの発動契機 | §4.7 のイベント一覧の名前をそのまま使う（`battleStart`, `turnStart`, `turnEnd`, `abilityUsed`, `abilityActivated`, `normalAttack`, `burst`, `damage`, `damaged`, `gaugeChanged`, `buffApplied`, `enterBattle`, `knockedOut` など） |
| 専用処理 | 逃げ道 | `{ "type": "custom", "id": "..." }` |

- 部品は 15〜25 種類程度から始め、表現できない効果が出たら追加する。
- 部品を追加したら、Zod スキーマ・registry・本ファイル・`DSL_PARTS.md`（部品の一覧表）を同時に更新すること。

### 10.2 意味論のルール
- `effects` 配列は**上から順に**処理する。
- `if` を並べた場合：当てはまったものを**すべて**実行する。
- `switch`：上から判定し、**最初に当てはまった 1 つだけ**実行する。どれにも当てはまらなければ `default`。
- 入れ子は可（Zod は `z.lazy` で検証）。**3 段を超える場合は `custom` に回す**。
- 「奇数回目」などの回数は、**今回の使用を含めて**数える（1 回目 = 奇数）。※仮置き（§11）
- **`useCount`**（条件・数値の部品）：アビの回数を数える。
  - `ability`：`"self"`（このアビ自身）またはアビ ID。
  - `scope`：`turn` / `battle`。
  - `kind`：`"used"`（既定。使用回数＝`abilityUsed`）または `"activated"`（発動回数＝`abilityActivated`）。§4.7 の「使用」と「発動」の区別に対応する。
- **`activateAbility`**：指定したアビの効果を発動させる（例：「バースト時、アビ 1 を発動」）。
  ```json
  { "type": "activateAbility", "character": "self", "ability": "eve_a1" }
  ```
  - `abilityActivated`（経路 `effect`）だけを記録し、`abilityUsed` は記録しない（**使用回数に数えない**。確定）。
  - 発動したアビの効果の中では、`"ability": "self"` は発動したアビを指す。
  - **発動したアビの CT は変えない**（確定。イヴのバーストで確認）。CT が 0 でなくても発動する。
  - ⚠️ 仮置き：コストを払わず、1 ターン上限・戦闘上限にも数えない（使用ではないため）。実機で確認すること（§11）。
  - アビの効果を処理する間に生じたイベントのアシストは、発動元（バーストなど）の処理が終わってからまとめて判定する（§6 アシストの判定タイミング）。
- **`changeCT`**：対象のアビの CT を変える。
  - `abilities`：`"self"`（このアビ自身）、`"all"`（対象キャラの全アビ）、アビ ID の配列、`{ "color": "red" }`（色で絞り込み）のいずれか。
  - `amount`（増減。例：`-1`）か `setTo`（その値にする。例：`0`）のどちらかを指定する。結果は 0 未満にも最大値超えにもしない。
- **`chosenAlly`（味方単体の対象選択）**：「味方 1 体に〇〇」のように、プレイヤーが対象を選ぶ効果に使う。選んだ相手はチャートの行動に記録する（§4.10）。選んでいない、または選んだ相手が場にいない場合は、その行動を使用不可として警告する。
  ```json
  { "type": "addBuff", "target": "chosenAlly", "buff": "攻撃力UP", "slot": "atkUp", "amount": 30, "duration": { "turns": 3 } }
  ```
- `damage` 効果は `category`（`normal` / `ability` / `burst`）と `hits`（ヒット数。**説明文に断りがなければ 1**。確定）を持ち、実行時に `damage` イベントを**ヒット数ぶん**発行する（§4.7）。ダメージ量は計算しないが、**イベントの発生は必ず記録する**（カウンター条件に使うため）。
  ```json
  { "type": "damage", "target": "enemy", "category": "ability", "hits": 10 }
  ```
- `damage` の属性は、省略時は発生源のキャラの属性を使う。説明文で属性が指定されている場合（「幻属性ダメージ」「全属性ダメージ」など）は `element` で書く。`damage` イベントの `element`（§4.7）はこの属性になり、`count` の `filter.element` で数えられる。発生源キャラの属性（`sourceElement`）は変わらない。
  ```json
  { "type": "damage", "target": "allEnemies", "category": "ability", "element": "phantom" }
  ```
  - 属性の値：`fire` / `water` / `wind` / `thunder` / `light` / `dark` / `phantom`（火・水・風・雷・光・闇・幻。§4.1）。
  - 「全属性ダメージ」は属性ごとに `damage` を並べて書く（属性ごとに 1 ヒットずつ、説明文の順に記録する）。
- **`hits` は数値のほか、数値の部品で書ける**。「n 回目の使用では n ヒット」のように、回数でヒット数が変わる効果に使う。
  ```json
  { "type": "damage", "target": "allEnemies", "category": "ability",
    "hits": { "useCount": { "ability": "self", "scope": "battle" }, "min": 1, "max": 10 } }
  ```
  - 数値の部品は条件と同じ集計を使い、比較（`gte` など）の代わりに**その値自体**を返す。`useCount`（アビの使用回数）、`count`（イベントログの集計。§4.7）、`token`（トークン数）。
  - `min` / `max` で値を範囲内に収める（任意）。
  - 評価の時点は条件と同じ（§6 コスト）。効果の中の `useCount` は今回の使用を含む（1 回目の使用 = 1）。
  - 数値の部品は、`hits` 以外の数値の欄（`gaugeUp` の `amount` など）でも使えるようにしてよい。使い道が見つかった時点で、本節に追記する。
- **`allEnemies`（敵全体）**：初期版は敵を 1 体として扱う（敵の数はスコープ外）。そのため `enemy` と同じく、`damage` イベントは**ヒット数ぶん（1 体分）**記録する。敵が複数のときにヒットを敵の数ぶん数えるかは未確定（§11）。データ上は単体と全体を区別して書いておき、将来敵の数を扱うときに使う。
- **`randomEnemy`（敵ランダム）**：「敵ランダムに 5 回」のように、ヒットごとに対象がランダムに決まるもの。初期版は敵 1 体なので `enemy` と同じに扱う。

**トークン・回数・繰り返しに関する部品**
- **トークンのグループ**（§4.2）：
  - 条件・数値の `token` は `name`（種類）か `group`（グループの合計）で数える。例：`{ "token": { "group": "旋律", "gte": 3 } }`。
  - `addToken` は上限（種類・グループ）を超えた分を破棄する。`consumeToken` は `"amount": "all"` で全部、`group` を指定するとグループ全体を消費する。
- **`trigger` 条件**：アシストの効果の中で、**そのアシストを発動させたイベント**の項目を参照する（§4.7 の項目名）。例：「使用したアビの色に応じて」は `{ "trigger": { "color": "red" } }`。
- **`source` フィルター**：`count` の `filter` とアシストのトリガーの `filter` で、発生源キャラをアシストの持ち主から見て絞り込む。`"self"`（自分）/ `"others"`（自分以外）。例：「自分以外の雷属性キャラが使用したアビ」は `{ "event": "abilityUsed", "filter": { "sourceElement": "thunder", "source": "others" } }`。
- **`alliesWhere` の `excludeSelf`**：「自分以外の味方全体」は `{ "alliesWhere": { "excludeSelf": true } }`。
- **`alliesWhere` の `includeSub`**：「サブメンバー含む」は `{ "alliesWhere": { "element": "thunder", "includeSub": true } }`。`includeSub` がなければメインだけ。
- **`partyAll` 条件**：「パーティ全体が雷属性キャラの場合」は `{ "partyAll": { "element": "thunder" } }`。サブを含めるかは未確定（§11。含めないで仮置き）。
- **フィルターの `token` / `assist`**：`tokenAdded`・`tokenConsumed` はトークン名 `token` で、`assistTriggered` はアシスト ID `assist` で絞り込む。
- **使用回数の上限を数値の部品で**：アビの `limit.perTurn` / `perBattle` は数値の部品でも書ける。上限が段階表で決まる場合（「消費数 0〜10 個なら 1 回、11〜19 個なら 2 回…」）は、数値の部品では書けないので、使用条件 `usable` に「段階に届いていて、今ターンの使用回数が上限未満」を `or` で並べて書く（アルテミスのアビ 1。`CHARACTER.md`）。
- **`removeDebuff` の `count: "all"`**：「状態異常を全回復」。
- **`undispellable`**：`addBuff` / `addDebuff` / `addStatus` に `"undispellable": true` を付けると「消去不可」。解除効果で消えず、サブに下がっても保持する（§4.4 の仮置き「原則解除、消去不可は保持」）。
- **`useCount` の `mod`**：「発動順に紅・黄・蒼・翠」のように回数を周期で分けるとき、`{ "useCount": { "ability": "self", "scope": "battle", "kind": "activated", "mod": { "by": 4, "eq": 1 } } }`（4 で割った余りが 1）。`parity`・`multipleOf` は `mod` の省略形とみなしてよい。
- **数値の部品の計算**：`mul`（掛ける）・`add`（足す）を付けられる。計算の順は `mul` → `add` → `min`/`max`。
  - 例：「紅の譜面の数 × 6 回」は `"hits": { "token": { "name": "紅の譜面" }, "mul": 6 }`。
  - 例：「譜面の数だけ CT を減らす」は `changeCT` の `"amount": { "token": { "name": "紅の譜面" }, "mul": -1 }`（`changeCT` の `amount` も数値の部品で書ける）。
- **持続ターンも数値の部品で書ける**：「発動する度に効果ターン延長（最大 5 ターン）」は `"duration": { "turns": { "useCount": { "ability": "self", "scope": "battle", "kind": "activated" }, "max": 5 } }`。
- **イベントの `filter` の `ability`**：アビ ID で絞り込む。`"self"` はその効果・アシストを持つキャラのアビではなく、**書かれている場所のアビ**を指すので、アシストの中ではアビ ID を直接書く。
- **`repeat`**：効果を指定した回数だけ繰り返す。「譜面の数に応じて回数増加」に使う。回数は数値または数値の部品。0 回なら何もしない。
  ```json
  { "type": "repeat", "times": { "token": { "name": "蒼の譜面" } },
    "effects": [{ "type": "addDebuff", "target": "allEnemies", "buff": "攻撃DOWN", "slot": "beethoven_atkDown", "amount": null,
                  "stack": { "max": "unknown", "duration": "unknown" }, "duration": { "turns": 6 } }] }
  ```
- **共有の効果（`sharedEffects` / `useEffects`）**：「アシスト 2 と同じ効果を発動」のように、同じ効果を複数の場所で使う場合、キャラ定義の `sharedEffects` に名前付きで 1 回だけ書き、`{ "type": "useEffects", "id": "..." }` で参照する。`recast` と同じく**読み込み時に展開**する省略形で、エンジンは展開後の部品だけを扱う。参照先のさらに中で `useEffects` を使うことはできない（循環を防ぐため）。
- **`note`**：どの効果にも任意で付けられる説明文。エンジンは使わない。ダメージ量の減衰（「減衰 40 万」）、「必中」、アイテムの生成など、初期版で扱わない説明文の情報を残すのに使う。
- `damage` と `performAttack` は別物として扱う。
  - `damage`：ダメージを 1 回発生させるだけ。ゲージ上昇・連撃・回数制バフの消費は起こさない。
  - `performAttack`：アビリティ効果の中で**通常攻撃（またはバースト）そのもの**を行う。§3-6 の攻撃ルーチンを呼ぶので、攻撃フェーズの通常攻撃と同じく、`normalAttack` イベント、区分 `normal` の `damage` イベント、ゲージ上昇、連撃判定、「〇回攻撃まで」の消費が発生する。
  - **確定**：アビ効果の通常攻撃でもゲージは上がり（連撃・上昇量アップのバフも通常どおり適用）、`gaugeGainBlocked` があれば上がらない。
  - **確定**：この通常攻撃でゲージが 100 に達しても、**その場ではバーストしない**。バーストは攻撃フェーズでそのキャラの番に判定される（§5）。
  - **確定**：カウンターへの計上は**通常攻撃として**数える。アビそのものの `abilityUsed` 1 件に加えて、`normalAttack` 1 件と区分 `normal` の `damage` をヒット数ぶん記録する。区分 `ability` の `damage` には数えない。
  - ⚠️ **仮置き**：「〇回攻撃まで」の回数制バフを**消費する**（アビの通常攻撃に乗って消え、攻撃フェーズの攻撃には残らない）。チャート上では、回数制バフが攻撃フェーズまで残っていない場合に警告する。`// TODO(spec)` を付け、実機で確認すること（§11）。
  - **確定**：アビ効果で通常攻撃したキャラも、**同じターンの攻撃フェーズで改めて攻撃する**（通常攻撃またはバースト）。アビの通常攻撃でゲージを溜め、攻撃フェーズでバーストする使い方ができる。

```json
{ "type": "performAttack", "attacker": "self", "kind": "normal", "times": 1 }
```
- `attacker`：攻撃するキャラ。対象と同じ書き方（`self` / `allAllies` / `alliesWhere`）ができる。
- `kind`：`normal` / `burst`
- `times`：攻撃を行う回数
- `gaugeAfter`（`kind: "burst"` のみ）：バースト後のゲージ。
  - `"zero"`（既定）：0 に戻る。
  - `"keep"`：消費せず、元のゲージのまま（[ずっといっしょ]ヘル など）。

```json
{ "type": "performAttack", "attacker": "self", "kind": "burst", "gaugeAfter": "keep" }
{ "type": "performAttack", "attacker": "allAllies", "kind": "burst" }
```

**アビ効果による即時バーストの仕様（確定）**
- 対象になったキャラだけが、**単発の行動として**バーストする。「味方全体が即座にバースト」なら、対象全員が 1 体ずつ順番に撃つ（順番は編成順と仮定。§11）。
- ゲージは 0 に戻る（`gaugeAfter: "keep"` の効果を除く）。
- 後ろのキャラへの **+10 の連鎖は発生しない**（§8.4）。
- 複数キャラが同時に撃っても、**チェインバーストは発生しない**（§8.5）。
- アビ効果でバーストしたキャラも、**同じターンの攻撃フェーズに通常どおり参加する**（確定）。攻撃フェーズまでにゲージを 100 に戻し、「発動」指定にしていれば、攻撃フェーズで再びバーストする。このバーストは通常の攻撃フェーズのバーストとして扱い、連鎖（§8.4）・チェイン／リンク（§8.5）の対象になる。
- **バーストに 1 ターンの回数制限はない**（確定）。ゲージさえ溜まっていれば、1 ターンに何回でも撃てる。チャートはアビ効果のバーストと攻撃フェーズのバーストを同じキャラ・同じターンに並べられるようにする。
- `burst` イベントは記録する（「バーストを〇回」などのカウンターに数えるかは未確定 §11）。イベントに `source: "ability"` を持たせ、攻撃フェーズのバースト（`source: "attackPhase"`）と区別できるようにする。
- ゲージ上昇・連撃の有無を上書きするオプションは、実機の挙動が確定してから追加する。

### 10.3 記述例
キャラ 1 体分の完全な定義例（条件付きコスト・即リキャ `recast`・`count` 条件のアシスト・`if` の分岐など）は、`src/content/characters/eve.json`（説明は `CHARACTER.md` のイヴの節）を参照。部品ごとの項目は `DSL_PARTS.md`。ここでは、部品ごとの書き方の例を示す。

交代・退場の例：
```json
{ "type": "swapWithSub", "target": "self" }
{ "type": "retire", "target": "self" }
```
- `swapWithSub`：対象を**即時に**生存しているサブの先頭と入れ替える（下がったキャラはその枠に入る。§4.4）。入ったキャラはそのターンの行動フェーズ・攻撃フェーズに参加する。下がったキャラは CT・HP・ゲージを保持してサブ枠で待機する（バフ・デバフの扱いは §4.4 の矛盾を参照）。
- `retire`：対象を退場させる。補充のタイミングは未確定（§11）。
- どちらも `enterBattle` イベント（入ったキャラ）を発行し、「登場時効果」のアシストを発動させる。

ポジション依存の例：
```json
{
  "type": "if",
  "cond": { "position": { "target": "self", "is": "front" } },
  "then": [{ "type": "addBuff", "target": { "alliesWhere": { "position": "front" } }, "buff": "攻撃力UP", "slot": "atkUp", "amount": 30, "duration": { "turns": 3 } }],
  "else": [{ "type": "addBuff", "target": { "alliesWhere": { "position": "back" } }, "buff": "防御力UP", "slot": "defUp", "amount": 30, "duration": { "turns": 3 } }]
}
```

複数分岐の例：
```json
{
  "type": "switch",
  "cases": [
    { "cond": { "token": { "name": "雷光", "gte": 5 } }, "then": [{ "type": "damage", "target": "enemy", "category": "ability", "hits": 5 }] },
    { "cond": { "token": { "name": "雷光", "gte": 3 } }, "then": [{ "type": "damage", "target": "enemy", "category": "ability", "hits": 3 }] }
  ],
  "default": [{ "type": "damage", "target": "enemy", "category": "ability", "hits": 1 }]
}
```
- ダメージ量は計算しないため、`damage` には倍率を書かない。分岐で変わるのがヒット数なら `hits` で表す（カウンターに影響する）。将来ダメージ計算を追加するときに倍率の項目を足す。

## 12. データ運用

- **1 キャラ 1 ファイル**の JSON（`src/content/characters/<id>.json`）。
- ビルド時に次の 2 種を出力する：
  - 一覧用インデックス（名前・属性・レアリティのみ）
  - キャラごとの詳細 JSON（編成に入れたときに遅延読み込み）
- 全キャラは 500 体超。**利用頻度の高いキャラから入力**し、残りは投稿で補う。
- wiki のテキストから Claude で定義 JSON の下書きを作り、人が確認する。曖昧な挙動は実機で確認する。
- キャラ画像は使用しない（名前とテキストデータのみ）。

### キャラデータの追加方法（当面）
0. 作り方は `CHARACTER_DATA_GUIDE.md`（説明文の言い回しと DSL の部品の対応表、説明文だけでは決まらず確認が必要な項目の一覧）に従う。
1. 資料（原文・wiki など）を `CHARACTER.md` にキャラごとの節として整理し、確定・仮置き・未確定と出典を書く。
2. DSL で定義の下書きを作り、`CHARACTER.md` に置いて確認する。説明文の「使用」と「発動」（§4.7）、「キャラの属性」と「ダメージの属性」（§4.1）は数え方が変わるので、読み分けて書く。DSL で書けない効果は `CHARACTER.md` の「DSL で書けない効果」に記録する。
3. 開発者が `src/content/characters/<id>.json` を追加し、ビルド時の Zod 検証を通す。JSON を作ったら JSON を正とし、`CHARACTER.md` の下書きはファイルへの参照に置き換える。
4. 実機の確認やクライアントの回答で分かったことは、JSON と `CHARACTER.md`（確定状況・検証の記録）を同時に更新する。

### 投稿フロー（後の版。当面は実装しない）
外部の人からキャラデータを受け付ける場合の案。最小構成を優先するため、**初期リリースにも実装手順（§16.1）にも含めない**。必要になった時点で着手する。
1. サイト内の入力フォームで定義を作成（ブラウザ上で Zod 検証）
2. 内容入りの GitHub Issue 作成画面を開く
3. レビュー → プルリクエスト → マージ
4. GitHub Actions がスキーマ検証 → ビルド → デプロイ

## 14. UI 要件

### 14.0 プレイ画面（メイン画面）
チャートの入力欄は見せない。プレイヤーは**ゲームのバトル画面に似た画面**を操作し、その操作がそのままチャートとして記録される（§4.10）。

**画面の構成**（ゲームのバトル画面の配置を参考にする）
| 要素 | 内容 | 操作 |
|---|---|---|
| ターン表示 | 現在のターン数とフェーズ | — |
| 敵の情報 | 敵の名前（任意入力）・属性・敵に付いたデバフ | — |
| キャラ列（右側に縦並び） | 英霊 → 前衛 1・2 → 後衛 1・2 の順。各キャラに名前、HP 割合、アビのアイコン（色付き。CT 中は残り CT を表示）、バーストゲージの値、このまま攻撃した場合にバーストするかの予測（§8.4） | キャラを押すとアビ一覧を開く |
| アビ一覧 | アビ名・色・CT・使用可否。使えない場合は理由（CT 中、回数上限、コスト不足、条件不足）を表示 | 押すと使用。`chosenAlly` のアビは対象のキャラを選ぶ |
| サブ表示 | サブ 1・2 のキャラと状態 | — |
| バースト発動の切り替え | パーティ全体で 1 つの「発動 / 温存」（§5） | 切り替え（ターンごと） |
| 攻撃ボタン | 攻撃フェーズを実行する | 押すと攻撃フェーズ → 敵フェーズの入力パネルへ |
| 敵フェーズの入力パネル | 攻撃ボタンの後に開く。被弾、戦闘不能、敵のデバフ付与、HP 割合の変更など、このターンの敵フェーズで起きたことを入力する（§4.10 手入力イベント） | 入力して「次のターンへ」 |
| 召喚攻撃 | 幻獣（定義が未確定のため初期版は表示のみ、または非表示。§4.3） | — |

- 状態が変わるたびに、エンジンの再計算結果で画面を更新する（§3-7）。アシストの発動、ゲージの増減、MISS などは、ゲームの演出の代わりに短い通知で表示する。
- 攻撃フェーズの連撃数は、通常表示の既定（1 段）で処理する。攻撃ボタンの横に連撃数を指定する切り替えを置き、指定した場合は `comboOverride` として記録する（§9）。
- 画面右上などに、**今の操作の記録をチャートとして見る**ボタンを置く（§14.1）。
- **ゲームの画像・アイコン・ロゴは使わない**（§12）。配置と操作の流れを似せるだけで、見た目は独自のものにする。アビの色はアイコンの色で表す。
- ゲームにある「回復」ボタン（アイテム使用）、Auto、救援要請、スタンプは対象外。

**巻き戻しとブランチ**
- チャート表示（§14.1）でターンや操作を選ぶと、プレイ画面がその時点に戻る。
- 戻った位置から違う操作をすると、**新しいブランチが自動で作られ**、元の記録は残る（§4.12）。記録を破棄することはない。
- 同じ操作をした場合は、既存の続きをそのままたどる（新しいブランチは作らない）。
- プレイ画面にはブランチの切り替えメニューを置き、今どのブランチの何ターン目かを常に表示する。

### 14.1 チャート表示（既出の要件のまとめ）
- チャートは**プレイ画面での操作の記録を表示する、閲覧用の画面**とする（直接は編集しない）。ターンごとに、誰が何のアビを使ったか、誰がバーストしたか、手入力イベントを表にして見せる。
- 共有・JSON 出力はこの画面から行う。
- 使用できない行動を警告表示する（§6）。プレイ画面では使えないアビは押せないが、記録した後で編成・ユーザー補正・設定を変えると、記録済みの操作が使えなくなることがある。その場合も記録は消さず、該当する操作に警告を付けて表示する。
- 各ターンの発動 / 温存の指定と、実際にバーストしたキャラを表示する（§5、§8.4）。
- 意図的に落とす戦術の計画用に、「この組み合わせで落とすと、どの枠に誰が入り、行動順がどうなるか」を表示する（§4.4）。
- 成功確率と、失敗原因の集計を表示する（§9）。
- 成功・失敗には影響しないが、次の事象を警告表示する：バフ・デバフの MISS と持続の上書き（§7.1）、デバフの下限到達（§7.2）、効果量が不明で重複を判定できない（§7.2）、連撃率が未入力のキャラ（§9）、回数制バフが攻撃フェーズまで残らない（§10.2）。

### 14.2 バフ・デバフのガントチャート
完成したチャートの上に、バフ・デバフ・状態異常の持続をガントチャートとして表示する。

**データ源**
- **イベントログ（§4.7）だけを描画する。** `buffApplied` / `buffOverwritten` / `buffMissed` / `buffConsumed` / `buffExpired` / `buffRemoved` から棒を組み立てる。UI 側で持続を独自に計算してはならない（エンジンと表示がずれるため）。
- 描くのは**通常表示（最低保証）の実行結果**（§9）。

**横軸**
- ターンを **行動・攻撃・敵** の 3 区間に分けて描く。1 ターン効果が「直後の敵攻撃まで」効いているかを判別できるようにするため（§7）。

**行**
- **キャラ × 枠**（§7.2）を 1 行とする。同じ枠のバフは同じ行に並ぶので、上書きや MISS が視覚的に分かる。
- **敵のデバフ**も「敵 × 枠」で行を作る。デバフの合計が下限（§7.2）に達している区間を色で示す。
- 枠を持たない状態異常は、キャラごとに効果名で 1 行とする。
- 行はキャラ単位で折りたためる。

**棒の描き方**
| 持続の種類 | 描き方 |
|---|---|
| ターン制 | 付与からターンエンド処理で消えるまでの棒 |
| 回数制 | 消費イベントの位置で終わる棒。棒の中に残り回数を表示 |
| 永続 | 右端まで伸びる棒 |

**マーカーと警告**
| 事象 | 表示 |
|---|---|
| MISS（§7.1） | ×印 |
| 上書きで持続が短くなった | 棒の切れ目 + 警告色 |
| 解除された | 終端マーカー（解除した効果を表示） |
| サブで待機中 | 行をグレー表示。バフ解除の扱いは仮置き（§4.4）であることが分かる表示にする |

**成功確率との連携**
- モンテカルロ実行で「このバフが切れて失敗」が多い場合、その棒を強調表示する。

**操作**
- 棒にカーソルを合わせると、付与元（キャラ・アビ）、効果量、残りターン／回数を表示する。
- 棒をクリックすると、付与した行動にチャート上でジャンプする。

工数の目安：エンジン側はイベントの記録のみで済むため、UI のみで 1〜2 人日。

### 14.3 Undo / Redo
プレイ画面の操作や各種設定の変更を元に戻す・やり直す。

**方式**
- 履歴の対象は**チャートデータだけ**（§3-7）。エンジンの状態は履歴に持たず、Undo/Redo のたびにチャートデータから再計算する。
- チャートデータは小さい（数 KB〜数十 KB）ため、**不変データのスナップショットを履歴に積む**方式とする（コマンドパターンで逆操作を書く方式は採らない。逆操作の書き漏れによるバグを避けるため）。
- 新しい編集をしたら、Redo の履歴は破棄する。
- 履歴の上限は 100 件（古いものから捨てる）。

**履歴に積む操作**
| 対象 | 例 |
|---|---|
| プレイ画面の操作 | アビの使用、バースト発動／温存の切り替え、攻撃ボタン（1 回の攻撃フェーズ全体を 1 操作） |
| ブランチ | ブランチの作成・名前の変更・削除、切り替え |
| 編成の変更 | キャラの追加・削除・入れ替え |
| 手入力イベント | 戦闘不能・被弾・HP 割合・敵のデバフ・連撃数の上書き |
| ユーザー補正 | アクセサリ項目、連撃率、詳細入力の効果（§4.9） |
| 設定 | 仮置き仕様の切り替え（§4.10 `settings`） |
| 読み込み | JSON・共有 URL からの読み込み（1 操作として積み、Undo で読み込み前に戻れる） |

**履歴に積まない操作**
- 表示設定（行の折りたたみ、拡大率、ガントチャートの表示切り替えなど）
- 成功確率の計算結果（派生データ。チャートデータが変わったら古い結果は無効として表示し、再計算させる）

**操作のまとめ方**
- プレイ画面では、プレイヤーの 1 操作（アビを 1 回使う、攻撃ボタンを 1 回押す）をそのまま 1 件とする。Undo はゲームでいう「1 手戻す」になる。
- ブランチ（§4.12）との違い：ブランチは「残しておきたい別案」を意図して持つもの、Undo は直前の操作の取り消し。
  - Undo で操作を取り消すと、今のブランチの先端が 1 つ前のノードに戻る。取り消したノードは、**他のブランチが使っていなければ**木から消す。他のブランチの途中にあるノードは消さない（そのブランチの記録を壊さないため）。
  - ブランチとして残したい場合は、取り消す前にブランチを作る。
  - 履歴はチャートデータ全体のスナップショットなので（上記）、Redo で取り消したノードもそのまま戻る。
- 数値入力欄は、確定（フォーカスが外れる、Enter）した時点で 1 操作とする。1 文字ごとに積まない。
- 1 回のユーザー操作で複数の変更が起きる場合（キャラを編成から外すと、そのキャラの行動も消えるなど）は 1 操作にまとめる。

**操作方法**
- ショートカット：`Ctrl+Z`（Mac は `Cmd+Z`）で Undo、`Ctrl+Shift+Z` / `Ctrl+Y`（Mac は `Cmd+Shift+Z`）で Redo。
- テキスト入力欄にフォーカスがあるときは、ブラウザ標準の文字単位の Undo を優先し、チャートの Undo は発動しない。
- スマホでも使えるよう、画面上に Undo / Redo ボタンを置く。履歴がないときは無効表示にする。
- Undo / Redo の直後に、何を戻したかを短く表示する（例：「T3 のイヴ アビ2 の追加を取り消しました」）。そのため履歴の各要素に操作の説明文を持たせる。

**保存との関係**
- 履歴はメモリ上だけに持ち、localStorage・JSON 出力・共有 URL には含めない（ページを再読み込みすると履歴は消える）。

工数の目安：0.5〜1 人日。

## 16. 実装の進め方（エージェント向け）

### 16.1 作業の順番
各手順で、その手順の仕組みのテストを Vitest で書いてから次へ進む。5 体の JSON（`src/content/characters/`）と `buffSlots.json` はすでにあるので、手順 2 以降はこれを入力として使う。

1. **雛形**：Astro + React + TypeScript + Vitest + Zod のプロジェクトを作る。ディレクトリ構成は §3。開発ツールを選び（§2）、同時に **`SETUP.md` を作成**して、ここまでの構築手順を書く（§16.3）。
2. **スキーマとデータ検証**
   - キャラ定義・効果 DSL・バフ枠・チャートデータ（§4.10、§7.2、§10）の Zod スキーマを `src/schema/` に作る。部品の項目は `DSL_PARTS.md` に合わせる。
   - 読み込み時の省略形の展開（`recast`、`useEffects`。§6、§10.2）と、展開前後が同じ挙動になることのテスト。
   - スキーマだけでは見られない検査（`slot` が `buffSlots.json` にあるか、トークン・アビ・アシスト・オプションの参照先があるか、入れ子が 3 段以内か）をする検証コマンド（例：`npm run validate:data`。`scripts/` に置く）。
   - 既存の 5 体の JSON と `buffSlots.json` がすべて通ること。通らない場合は、JSON・スキーマ・`DSL_PARTS.md` のどれが誤りかを切り分けて直す。
3. **エンジンの骨組み**：状態（§4.5、§4.6）、イベントログとキュー（§4.7、§6.1-4）、ターン進行（§5）、CT とアビの使用判定（§6）、ゲージ（§8）、攻撃ルーチン `performAttack`（§3-6）。
4. **操作の記録の再生**：チャートデータ（§4.10）の操作（`useAbility`・`setBurst`・`attack`・`enemyPhase`・`nextTurn`）を根から先端まで再生して各時点の状態を求める部分。使えない操作の判定と警告（§6、§14.1）もここで作る。
5. **効果部品とアシスト**：registry（§10.1）の効果・対象・条件・数値の部品、アシストの処理順（§6.1）と設定の切り替え（§16.2）、安全装置（§3-8）。
6. **バフ・デバフ**：枠と重複ルール、累積型、持続の 3 種類（§7）。イヴのアビ 2・3 など 5 体のアビが使うため、キャラのテストより先に作る。
7. **編成・交代・ユーザー補正**：戦闘不能と補充・交代（§4.4。手入力イベント）、ユーザー補正とキャラのオプション（§4.9）。
8. **5 体のテスト**：5 体の JSON を読み込み、各キャラの「主に確かめる仕組み」（§15.2）が動くことを Vitest で確かめる。イヴから始め、ベートーヴェン・シャイターン・アモン・アルテミスの順に進める。
9. **成功確率**：乱数注入と厳格判定（§9）。
10. **保存と読み込み**：localStorage と JSON の入出力（Zod で検証。§4.10）。
11. **UI**：プレイ画面（§14.0）→ チャート表示（§14.1）→ Undo/Redo（§14.3）→ ブランチ（§4.12）→ ガントチャート（§14.2）。
12. **CI とデプロイ**：GitHub Actions（検証 → テスト → ビルド → デプロイ）と Cloudflare Pages の設定（§2）。
13. **実プレイ記録の突き合わせ**（§15.4）：クライアントから届いた実プレイの記録を `tests/cases/` に置き、エンジンの結果と比べる。届いた分から順に進めてよい。

### 16.2 守ること
- **エンジンは UI に依存させない**（§3-1）。エンジンのテストは UI なしで動くこと。
- **未確定の項目を勝手に決めない。** 仮置きで実装する場合は `// TODO(spec): §番号 内容` を付ける。
- **仮置きの仕様は設定で切り替えられるようにする**（§4.10 `settings`）。現在の設定項目：

  | 設定 | 既定値 | 内容 |
  |---|---|---|
  | `assistReentry` | `true` | 同じタイミング内で前のアシストに戻って発動するか（§6.1-3） |
  | `assistEventOrder` | `"queue"` | アシストが生んだイベントを後回しにするか割り込むか（§6.1-4） |
  | `assistTiming` | `"afterAbility"` | アシストの判定をアビの効果をすべて処理した後にするか（§6） |

  その他の仮置き（交代時のバフ解除 §4.4、回数制バフの消費 §10.2、敵の上昇無効の範囲 §8.3、ターンエンド処理の順番 §5）は、必要になった時点で同じ形の設定にしてよい。
- 状態は二重に持たない。回数はイベントログから求める（§3-3、§4.5、§4.7）。
- 効果 DSL の部品を追加・変更したら、Zod スキーマ・registry・本ファイル §10・`DSL_PARTS.md` を同時に更新する（§10.1）。
- バフ・デバフの枠は `src/content/buffSlots.json` に足してから使う（§7.2）。
- Zod は `zod` パッケージから import し、エンジン（`src/engine/`）と `src/schema/` から `astro:*` を import しない（§2、§3-1）。
- 投稿データ・読み込みデータにコードを含めない。読み込み時は必ず Zod で検証する（§3-4、§4.10）。
- ゲームの画像・アイコン・ロゴを使わない（§12、§14.0）。
- 仕様の解釈を変えたり新しい事実が分かったりしたら、**コードとテストと本ファイルを同時に更新する**（§13）。§11 の確認事項が解決したら、チェックを付けるか削除し、本文の「仮置き」「未確定」の記述も直す。
- 開発環境に関わる変更をしたら、**同じ作業の中で `SETUP.md` も更新する**（§16.3）。
- キャラ固有の事実（CT・効果量・ヒット数・挙動の確認結果など）は `CHARACTER.md` に書き、本ファイルには書かない。キャラのデータを変えたら、JSON と `CHARACTER.md` を同時に更新する（§12）。

### 16.3 SETUP.md（開発環境の構築手順）
リポジトリ直下に `SETUP.md` を置き、**新しい開発者（人・エージェント）が、このファイルだけを見て開発を始められる**状態に保つ。仕様は本ファイル（AGENTS.md）、環境構築は SETUP.md と役割を分ける。

**書く内容**
| 項目 | 内容 |
|---|---|
| 前提 | 必要なツールとバージョン（Node.js、パッケージマネージャー、Git）。OS ごとの違いがあれば併記。§2 で指定していない開発ツールは、選んだものと理由も書く |
| バージョンの固定 | Node.js のバージョンを固定するファイル（`.nvmrc` など）と、`package.json` の `engines`。SETUP.md にもその値を書く |
| 取得と初期設定 | リポジトリの取得、依存パッケージのインストール、環境変数（必要な場合。`.env.example` を用意し、値の意味を書く） |
| 日常のコマンド | 開発サーバーの起動、テスト（全体・1 ファイルだけ・監視モード）、型チェック、Lint・整形、本番ビルド、ビルド結果の確認。それぞれ実行するコマンドと、成功したときに何が表示されるか |
| ディレクトリの説明 | 主要なディレクトリと置くもの（§3 の構成と一致させる） |
| キャラデータの追加 | `src/content/characters/` への JSON の追加手順と、検証コマンド（§16.1 手順 2）の実行方法。JSON の作り方は `CHARACTER_DATA_GUIDE.md`、資料と確定状況の記録は `CHARACTER.md` を参照する（§12） |
| テストケースの追加 | `tests/cases/` に実プレイの記録を追加する手順（§13） |
| デプロイ | Cloudflare Pages の設定値（ビルドコマンド、出力ディレクトリ、Node.js のバージョン）と、GitHub Actions の動き |
| よくあるトラブル | 実際に遭遇した問題と解決方法。作業中に詰まって解決したものは必ず追記する |

**書き方のルール**
- コマンドはコピーしてそのまま実行できる形でコードブロックに書く。手順は番号付きで、上から順に実行すれば動くようにする。
- 「〜をインストールしておく」のような省略をせず、確認のコマンド（例：`node -v` で期待されるバージョン）も書く。
- 依存パッケージの追加・削除、スクリプトの追加・変更、設定ファイル（Astro、TypeScript、Vitest、Lint など）の変更、環境変数の追加、CI・デプロイ設定の変更をしたら、**その作業の中で SETUP.md を更新する**。
- 書いた手順は、可能な範囲で実際に実行して確かめる。確かめていない手順にはその旨を書く。
- 末尾に最終更新日を書く。
